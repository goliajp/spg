## 1. Two ways an index could return less than it should

### 1.1 An expression index stood in for a column index

**You are not affected today, and we checked rather than assumed.** It
is dialect-independent — PostgreSQL wire, MySQL wire, embedded, all the
same — and it reaches **7.38.16 and 7.38.17 only**. We ran the shape
below against each published image in turn: `7.38.6` through `7.38.15`
answer correctly, `7.38.16` and `7.38.17` do not, and `7.38.18` does
again. If you upgrade straight from 7.38.6 to 7.38.18 you never meet it.

We are telling you anyway, because a defect that was live in the two
most recent releases is one you would have met had you upgraded a week
ago, and because we got the story wrong ourselves first: the first draft
of this letter said it had been present since 7.38.6. It had not, and
the image test is what said so.

```sql
CREATE TABLE ix (id INT PRIMARY KEY, s TEXT);
INSERT INTO ix VALUES (7, 'Row7');
CREATE INDEX ix_lower ON ix ((lower(s)));   -- an expression index
SELECT * FROM ix WHERE s = 'Row7';          -- before: no rows
```

"Is there an index on column `s`?" returned the *expression* index built
over `lower(s)`, and the plan then probed it with `'Row7'` — a value
that is not in it, because every entry is lowercased. Nothing matches
and the answer is an empty result.

It needs two things to appear: an expression index, and a query filtering
the same column directly. It is silent when it does.

**Where it came from is the part worth reading.** 7.38.16 made an
expression index actually hold the *expression's* values. Before that it
held the column's own values — which is why the same lookup returning it
still gave right answers, and why every release up to 7.38.15 is clean.
That change was itself a fix, and a real one; what did not change with it
was the lookup that answers "is there an index on column `s`". It kept
returning the expression index, and the probe built from the column's own
value then asks a tree of `lower(s)` a question its keys cannot answer.

A test asserting "the index is used" would have passed: it *was* used.
The lower-case row in our own fixture is the trap — `'row8'` and
`lower('row8')` are the same string, so a fixture built from lower-case
data passes with the defect present.

### 1.2 An index on a column with a locale collation dropped rows

New in this release's own work, caught before it left the gate, and
described here because the shape is instructive. When a column declares a
collation, its index entries are built from the collation's sort key —
and a lookup that built its probe from the raw bytes instead is asking a
different question of the same structure. It finds nothing. Two of the
three sites that could do this were ours to fix; one was in composite
indexes, where only the leading columns up to the collated one can be
used as a prefix.

The gate's differential corpus caught both. **No released build shipped
either**, and that is measured rather than assumed: the same shape run
against 7.38.15, 7.38.16 and 7.38.17 answers correctly on all three.

What those three *did* answer was a warning, on every `CREATE TABLE`
declaring a collation:

```
WARNING: column "s" declares COLLATE "de-DE-x-icu"; SPG orders it by
"de-DE-x-icu", but RANGE COMPARISONS (BETWEEN, <, >) still compare by
bytes — they may return a different row set than "de-DE-x-icu" implies
```

**That warning is gone in 7.38.18, because the limitation it described
is gone.** A declared collation now reaches `<`, `BETWEEN` and the index
keys, checked against PG 18.4. The only case that still warns is a
collation this build records but cannot perform, and it says so in those
words — a warning that has stopped being true is worse than no warning.

## 2. The PostgreSQL compatibility matrix reaches zero

`PG_MIGRATION.md` — the page a team reads before deciding whether to
switch — carried twenty-six ❌. We re-measured every one of them against
this build.

**Twenty-one were already false** — `UUID`, `TRUNCATE`, `RIGHT JOIN`,
`FULL OUTER JOIN`, `INTERSECT`, `EXCEPT`, `LATERAL`, `CREATE SCHEMA`,
domains, composite types, partitions, RLS and the rest. The table
described a 7.12.10 SPG and had not been re-run in twenty-six releases.

**Of the five that remained, three were not gaps either.** `pg_dump` and
`pg_restore` work and have for a long time — we ran pg_dump 18.6 against
this build and restored the result both ways. `COPY … FROM STDIN` works
over the wire; an earlier probe of our own had exercised a different,
in-process path and reported a gap that was not there. And
`SELECT … AS OF TIMESTAMP` was marked missing against PostgreSQL, which
answers `syntax error at or near "timestamp"` to it — that row should
never have been a ❌.

**Two were true, and both are now closed:**

- **Spanish, French and German full-text search.** Snowball's stemmer
  and stopword list for each, written from the published algorithms —
  not ported — and verified word for word against PostgreSQL 18.4 over
  **6,057 words**: 1,847 Spanish, 2,193 French, 2,017 German, out of
  corpora of 6,183 lines — the rest are stopwords and words that
  tokenise into more than one lexeme, which are not stemming questions.
  Zero disagreements. `to_tsvector`, `to_tsquery` and `ts_headline` all
  follow the configuration.

- **`pg_hba.conf`-style host-based authentication.** `SPG_HBA_FILE`
  names a file in PostgreSQL's own format:

  ```
  host    all   all   127.0.0.1/32   trust
  host    all   all   all            scram-sha-256
  ```

  `local` / `host` / `hostssl` / `hostnossl`, `all` or a named database
  and user, an address with a prefix length, and `trust` / `reject` /
  `scram-sha-256` / `password`. The first matching line decides, as in
  PostgreSQL; a connection matching no line is refused with PostgreSQL's
  own message; and a file that does not parse stops the server at
  startup rather than being silently ignored — a half-read
  authentication policy is worse than none.

The verdict column now holds no ❌ at all.

A stale ❌ costs more than a missing feature. Nobody reports it: the
people it turns away never arrive.

The MySQL and MariaDB drop-in pages had the same disease and got the
same treatment — every claim on both re-measured against a live MySQL
9.7.2 and MariaDB 12.3.2. **Nine of nine and five of five now work**,
where the two pages had carried thirteen `partial` and `pending` notes
between them — ten on the MySQL page, three on the MariaDB one —
describing work that had since been done.

## 3. Collations, end to end

A database can now be created with a collation, and it means what it
means in PostgreSQL:

```sql
CREATE DATABASE app LC_COLLATE 'de_DE.utf8';
```

Every text column that does not name its own collation inherits it, and
that default now survives a dump and reload. A collation that does not
exist is refused with PostgreSQL's own error rather than silently
falling back to byte order — the failure mode where a column quietly
sorts differently from the one it was supposed to match.

`pg_collation` lists **880** collations where it had listed three. It had
become what `pg_settings` was earlier in this same version: the feature
worked, `information_schema` agreed, and the catalogue everything else
reads said no such collation existed. pg_dump's `COLLATE` restoration,
psql's `\dO`, and any ORM binding a language-specific column all read
that table.

**Every comment form both dialects have**, including the two where the
dialects contradict each other. PostgreSQL's block comments nest;
MySQL's do not — `SELECT /* a /* b */ c */ 1` is `1` on PG 18.4 and a
syntax error on MySQL 9, and `SELECT /* a /* b */ 1` is the other way
round. No single reading satisfies both, so the dialect decides. SPG had
neither. `#` line comments, `/*+ hint */` and MariaDB's
`/*! STRAIGHT_JOIN */` are all handled — the last with a check that a
`/*! … */` holding real SQL still executes it, because treating those as
comments would silently swallow half of a mysqldump.

**Thirty-two runtime switches the code reads were not on the tunables
page** — 63 documented before, 95 now. They are now, with their defaults read out of the source rather
than remembered. One of them was worse than undocumented:
`SPG_FREEZER_DISABLE=false` *disabled* the freezer, because the reading
was "is the variable set to anything at all".

## 5. What we fixed about ourselves

**Our own lint runs were hiding their findings.** Six times this cycle
the release gate reported a lint failure that our local runs called
clean, and six times we diagnosed it wrong — a stale build cache, we
said, every time. The gate treats warnings as errors; the local command
did not, and then filtered its output for lines beginning `error`, which
removed every finding there was. Clearing the cache appeared to help
only because the recompile printed the findings again where we could see
them. A negative control refuted the diagnosis on the sixth attempt.
**Two of the six were real errors sitting in committed code.**

**The gate's cross-version open only ever made a one-release hop.** The
step that opens a released data directory with the new binary chose the
*newest* previous release — the hop least likely to break, since it is
almost always the same file format on both sides. The far hop, which is
the one an installation several releases back actually makes, had no
check. It now opens the oldest and the newest fixture we hold and names
both in the verdict.

**A test written straight after the code it tests can copy the bug.**
Twice we wrote an expectation from what our own engine printed rather
than from what the engine we stand in for prints. One of those fixtures
then argued for the defect for a full release.

**A measurement can be blocked by an earlier bug and read as a result.**
Removing a guard three times changed nothing, which we read as "the
guard is dead code". It was not: a defect upstream of it was intercepting
the query before it could reach the guard at all. Fixing the upstream
defect made the same removal fail immediately.

## Still open, named rather than left out

- **Sorting under a locale collation is about 1.3x behind PostgreSQL**,
  in-process, and we have not closed it. PostgreSQL builds an
  *abbreviated* sort key — a few bytes that settle most comparisons
  without touching the full key — and the ICU binding we use does not
  expose one. The measurements: one ICU comparison costs about 50 ns
  (9.9 ms for 200,000 of them), and sorting 200,000 values needs roughly
  3.5 million comparisons — so about 175 ms, derived from the per-call
  figure rather than timed end to end. Building all 200,000 sort keys up
  front costs 138 ms measured, and the sort over them is then 0.28 ms of
  `memcmp`. An 18 % saving that still loses, which we would rather
  report as a measurement than dress up as a fix.
  Byte-wise collations, which is every column that has not asked for a
  locale, are unaffected.
- **`COLLATE` on an arbitrary expression.** `ORDER BY col COLLATE
  "de-DE-x-icu"` works; `ORDER BY (a || b) COLLATE "de-DE-x-icu"` does
  not parse.
- **The three shapes of yours still behind PostgreSQL 18** — §4.
