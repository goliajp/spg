## 2.1 A SQL function declared to return an array returned NULL — fixed

Your five cases, on 7.38.4:

| | PG18 | SPG 7.38.3 | SPG 7.38.4 |
|---|---|---|---|
| `RETURNS bigint` — the scalar control | `7` | `7` | `7` |
| `RETURNS bigint[]` | `{1,2}` | NULL | `{1,2}` |
| `RETURNS text[]` | `{a,b}` | NULL | `{a,b}` |
| the same expression inline | `{1,2}` | `{1,2}` | `{1,2}` |
| `vk('4.10.0') >= vk('4.2')` | `t` | NULL | `t` |

The cause, since it explains why the body was fine and the value was
not: `def.returns` holds the type as **you wrote it** — `bigint[]` —
while the internal cast target spells the same type `bigint_array`. So
coercing the body's value to the declared return type could not resolve
the bracket spelling, and an `or_else(NULL)` under that coercion turned
"I could not resolve this type" into "the answer is NULL". No error
anywhere. Your `RETURNS bigint[]` parse fix in 7.37.25 got the
declaration through; this was the next link, one layer down.

The same line existed at **both** coercion sites — a body that is one
expression, and a body with its own FROM. Fixing the one your repro hit
would have left the other, so the spelling is now a single shared
helper and both shapes are pinned, including
`RETURNS bigint[]` over an `array_agg` with a FROM.

`sentori_version_key` should work, and step 54 with it.

## 6a `pipeline.rs:547` — we match PG's refusal now, as you asked

Thank you for measuring both halves, and for saying plainly which part
of our flag was wrong. The distinction you found is the whole of the
implementation:

* **Deduced** (`PREPARE q AS …`) — now refused, with PG's message:
  `inconsistent types deduced for parameter $4 … bigint versus integer`.
* **Declared** (`PREPARE q (…, bigint, …) AS …`) — accepted and runs,
  as in PG. sqlx declares, so this is the path your production has
  always taken, and refusing it would break every driver that does the
  right thing.

Both halves are pinned, and so is the negative: an ordinary `PREPARE`
whose parameter is used consistently, or used in only one place, still
prepares. We re-ran your 211 statements with the refusal in place —
209 still describe byte-identically to PostgreSQL 18, 0 SPG-only
errors. It catches the conflict and nothing else.

On your correction to yourself: adding the `::bigint` casts anyway,
because "a statement whose validity depends on the driver's inference
is invisible from the statement", is the better reason of the two. We
would have done the same.
