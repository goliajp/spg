**One theme, and it is the sharpest one we have shipped: adding an index
changed the answer.** Four separate places. In two of them the answer it
changed to was *nothing at all*.

An index is supposed to be invisible. It may make a query faster or
slower; it may never make it return different rows. Everything below is
that rule being broken, and every number is measured against the engine
we are standing in for — PostgreSQL 18.4 or MySQL 9.7.1 — not reasoned
out.

## 1. An indexed join returned the empty set

On a case-insensitive text column — the MySQL default —
`a JOIN b ON a.s = b.s` over `'alpha'` and `'ALPHA'`:

|  | MySQL 9.7.1 | SPG, no index | SPG, indexed |
|---|---|---|---|
| inner join | 1/10, 2/20 | 1/10, 2/20 | **(no rows)** |
| left join | 1/10, 2/20 | 1/10, 2/20 | 1/NULL, 2/NULL |

7.38.13 and 7.38.15 fixed this comparison in the scan and in the hash
join. The *indexed* nested-loop join kept probing the B-tree by bytes,
and MySQL's default collation does not compare by bytes. So the same
query answered correctly until someone added an index to the column.

## 2. And the same cause, in four more shapes

|  | MySQL 9.7.1 | no index | indexed |
|---|---|---|---|
| `s = 'ALPHA'` | 1 | 1 | **(no rows)** |
| `s IN ('ALPHA','BETA')` | 1,2 | 1,2 | **(no rows)** |
| `s BETWEEN 'ALPHA' AND 'DELTA'` | 1,2,4 | 1,2,4 | 2 |
| `ORDER BY s LIMIT 2` | 1,2 | 1,2 | 2,3 |

on `TEXT`, `VARCHAR` and `CHAR` alike. Whether a byte-keyed index can
answer a comparison is now **one decision in one place**, asked by the
equality seek, the `IN` seek, both range seeks, the ordering walk and
the join. A column that declares `COLLATE utf8mb4_bin` is byte-wise and
keeps every seek; anything else under MySQL falls back to the scan,
which costs time and not rows.

A `CHAR` column was wrong even with no index at all: `IN`, `>=` and
`BETWEEN` kept both the case and the trailing padding, so
`s BETWEEN 'ALPHA' AND 'DELTA'` over alpha/Beta/GAMMA/delta answered
1,4 where MySQL answers 1,2,4 — `'Beta'` lost to case and `'delta   '`
lost to its own eight characters.

## 3. Why the gate never caught any of it

Because the gate could not ask.

Our corpus has a `mysql/` directory. The runner that executes it had no
notion of a SQL dialect at all, so every file in it has been running in
**PostgreSQL** dialect since the day it was created — asserting that
MySQL *syntax* is accepted, and nothing whatsoever about MySQL
*semantics*. The directory name looked like coverage and was not.

There is a `dialect mysql` directive now, and every table above is a
fixture. We would rather tell you this than let the next one through the
same hole.

## 4. The full-text index PostgreSQL tells you to create

`CREATE INDEX ON d USING gin (to_tsvector('english', title || ' ' ||
body))` is the ordinary spelling, and we refused the DDL outright — so
did `coalesce(title,'')`, so did `(meta -> 'tags')`. PostgreSQL 18.4
accepts all three. A schema that used any of them did not load, which is
a worse failure than a slow query: it arrives before you run one.

The single spelling that did work — `to_tsvector('english', body)` on a
bare column — built the index with the wrong tokeniser and then
**returned no rows**. It stored `lazy`; the query asked for the English
stem `lazi`. One row without the index, none with it, one in PostgreSQL.

All four work now, and the index is used: **0.013 ms against 50.167 ms**
for the scan at 20,000 rows.

## 5. An index on an expression was pure cost

`CREATE INDEX ON t (lower(s))` built, answered correctly, and nothing
ever chose it. The B-tree was being filled with the values of `s` under
an index whose key is `lower(s)` — keys nothing could match.

So it charged you for writes and returned nothing for reads. An insert
on a 20,000-row table ran 5.20 µs against 2.70 µs with no index at all,
while the same `SELECT` ran within one percent of itself with the index
and without.

| | 10,000 rows | 100,000 rows |
|---|---:|---:|
| before | 0.753 ms | 7.739 ms |
| after | **0.004 ms** | **0.004 ms** |

The write cost is unchanged — the same maintenance, now on keys
something can read.

`CREATE UNIQUE INDEX ON t (lower(email))` rejected duplicates correctly
all along, but did it by re-reading the whole table on every insert:
0.43 ms per insert at 2,000 rows, **3.9 ms at 20,000** — a cost that
grew with your data. Now 6.0 µs at both, level with a unique index on a
column.

## What we looked for and did not find

`IndexKey::from_value_for_column` — the place a probe is built from a
column and a value — appears in five more spots than the ones above. We
measured the shapes they serve rather than reading them: an `IN`
subquery, `EXISTS`, a scalar subquery, a predicate pushed onto a joined
table, and two `count(*)` tallies answered from index keys with no row
re-check. **Nine shapes, all agreeing with MySQL 9.7.1 with an index and
without.** Only the join needed fixing.
