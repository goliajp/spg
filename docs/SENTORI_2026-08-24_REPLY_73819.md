## 1. Your §2.1 — the CTAS command tag

Fixed, and the differential found four more forms while confirming the
one you named. Measured on PG 18.4, because the two that are **not**
`SELECT <n>` are the ones reasoning would have missed:

| statement | PostgreSQL 18.4 | SPG before |
|---|---|---|
| `CREATE TABLE t AS SELECT …` | `SELECT 3` | `CREATE TABLE` |
| `… WITH NO DATA` | **`CREATE TABLE AS`** | `CREATE TABLE` |
| `SELECT … INTO t` | `SELECT 3` | **syntax error** |
| `CREATE MATERIALIZED VIEW …` | `SELECT 3` | bare `CREATE` |
| `… MATERIALIZED VIEW … NO DATA` | **`CREATE MATERIALIZED VIEW`** | bare `CREATE` |

All five were wrong. The count was wrong too — the executor returned zero
for the materialised rows, so even a correct tag would have said `SELECT
0`.

**One of them had a test defending it.** The materialized-view case was
pinned as `CREATE`, under a comment reading *"a recorded delta (PG:
SELECT <n>)"* — the right answer and the wrong assertion in the same
breath. A divergence written down and then made the expected value is a
defect with a test protecting it, and this one survived because the note
read like a decision.

`SELECT … INTO` had never parsed at all, while a comment in our AST has
said since v7.38 that it and CTAS lower to the same node. Making it work
took three layers, and each was a classifier deciding *is this a read*
from the first word: the parser, the read/write dispatch, and the tag.
`CREATE TABLE … AS` was right at all three, so the two spellings of one
statement disagreed about all three.

## 2. Your §2.2 — the UDF result type

Fixed. You were right that the executor was never confused; only the type
travelling in the `RowDescription` was. `SELECT 7::bigint, f_sql()` now
right-aligns both cells.

The cause is worth telling you because it is the same shape as §1: the
projection called the catalog-**less** type walker, and the user-function
arm is the one arm of that walker that needs a catalog. `Describe` had
been given one in v7.38.7 and the projection had not, so the two
disagreed about the same expression — which is the disagreement you
reported one round earlier in a different place.

**The first pin we wrote for it did not work.** We wrote a corpus file
with `query I`, believing the runner's `I` checks the column's type. The
negative control — put the old call back — left it green: the runner
compares rendered values and never asks the schema, so that defect could
not be expressed there at all. Asserting the column type directly, the
same negative control reads `left: [Text] right: [BigInt]`.

## 3. Your §3 — `CREATE DATABASE … LC_COLLATE`

**`pg_database` now lists every name the server answers to**, so `dd` is
in the catalogue that `psql \l`, a migration tool's "does this database
exist" and a backup script all read.

Your second point cannot be fixed while SPG serves one database: a
statement naming `dd` does change how `d` compares text, and under
PostgreSQL's model nothing a `CREATE DATABASE` does can reach an existing
one. What can be fixed is the silence, and it is: the statement now warns
that the names are aliases onto one database and that the collation
applies here too. You are right that the dangerous case — indexes built
under one collation, probed under another — was already guarded; that
guard is why you could not make it drop rows.

The first version of our fix recorded the *keyword*: `pg_database`
listed a database called `database`.

## 4. What was behind them

- **`SELECT 1::xid8` returned `1`** where PostgreSQL answers `cannot cast
  type integer to xid8`. **Us accepting what PostgreSQL rejects is the
  worse direction**: code PostgreSQL would have stopped runs here, and
  the difference surfaces somewhere else, later. Nobody had recorded it;
  it surfaced because a comment two lines above it was being re-measured.

- **`nextval`, `setval`, `pg_advisory_*` and `lo_*` all returned
  `?column?`** where PostgreSQL names the column after the function. They
  are evaluated by a pass that replaces the call with the literal it
  produced, and a literal has no name to figure out. An ORM reading
  column names got `?column?` for every one.

- **`pg_advisory_unlock` did not warn** when you do not hold the lock.

- **Starting the server cost the size of a directory it does not own.**
  It swept the whole system temp directory at every start; on our machine
  that had reached 61,708 entries and 30 GB, and one `readdir` took **95
  seconds**. Every server our own tests spawned waited a minute and a
  half before it could listen — and the failures read exactly like a busy
  machine, which is what we had been calling them.

## 5. Performance

A regression we shipped in v7.38.18, found by auditing the three shapes
of yours still behind PostgreSQL. It is not one of them.

`WHERE kind = 'click'` over 200,000 rows, interleaved on one box:

| | |
|---|---|
| database collation `C` | 2.2–3.1 ms |
| database collation `en_US.UTF-8` | **58.3–76.2 ms** |
| PostgreSQL 18.4 | 1.5–4.4 ms |

Twenty-six times our own byte path, thirty times PostgreSQL, on the most
ordinary predicate there is. Two causes, both work done per row that
belongs once per query: a folding step that copied each side into a fresh
string and left it exactly as it found it, and a call that parsed the
locale and built a whole ICU collator **on every comparison**.

After: text equality 2.6 ms, level with PostgreSQL. Ordering went 62.5 →
15.3, and a collated `ORDER BY` 328 → 264 ms against PostgreSQL's 158 —
still 1.67x behind, named rather than left out. That last one cost 18 MB
of peak memory for its 20 % of time, and we would rather give you both
numbers than the flattering one.

**This does not change your figures**, and we checked rather than
assumed: our image starts a database under `C`, so none of it applies to
a deployment running the stock image. Your three shapes are where they
were.

**Which raises something you should know, and it touches your gate 2
conclusion directly.** `postgres:18` starts under `en_US.utf8` and sorts
`apple, Bob, Zebra`; our image starts under `C` and sorts `Bob, Zebra,
apple`. A team moving off the standard PostgreSQL image gets a different
row order from us, silently.

We have not flipped our default, and the reason is a trade rather than an
oversight: doing it hands every deployment the ordering cost above. Close
the ordering gap, then flip.

**But there is a second reason, and it is yours.** Your divergence note
found that the eight collation-sensitive probes differ between
`postgres:18` and `postgres:18-alpine` — that the ordering of your
project and version listings already depends on which Postgres a
deployment runs, and that your documentation does not say so. If we
flipped our image default, we would make that change *for* your
`docker-compose` users without their asking. On names shaped like yours:

```
SPG under C            Beacon, Zephyr, _internal, apollo, atlas
SPG under en_US.utf8   apollo, atlas, Beacon, _internal, Zephyr
PostgreSQL 18 (glibc)  apollo, atlas, Beacon, _internal, Zephyr
```

We match PostgreSQL exactly under a locale and differ from it under `C`,
which is the whole of the question. When we do flip it, it will be a
release that says so in its first line, not a default that moves under
you. If you would rather have the PostgreSQL ordering before then,
`SPG_LC_COLLATE=en_US.utf8` on the container does it today — and on the
data you described the cost lands on `ORDER BY p.name` and `ORDER BY
r.name`, which is where you already said the exposure is.

**As it stands you are unaffected either way** — `postgres:18-alpine`,
which you run, declares `en_US.utf8` and sorts by bytes anyway, because
musl carries no locale data. Your gate 2 result holds: what we do matches
what you deploy.

The harness is at `xbench/dropin-perf/`, self-contained, with a README
written for someone who does not have our checkout. It needs `docker`,
`psql` and `awk`.

## 6. What we got wrong this round

Your §7 described running a capability test in the same container as a
measurement. We did the same class of thing, in our release gate, and it
had been true for months.

**Our testbed exports `LANG=en_US.UTF-8`.** Every server our suite starts
inherited it, so the perf sweep's baseline leg — the one every comment
calls the `C` leg — had been running under a locale collation the whole
time. Which means the locale-collation panel we added *in this same
release, to catch exactly the regression in §5*, was comparing
`en_US` against `en_US` and reporting no losses. **An instrument that
cannot fail is not a check**, and this one was added by the same hand, in
the same version, two hours earlier.

It surfaced because a panel went red with numbers that made no sense
beside the local ones: PostgreSQL's times were nearly identical on both
machines while ours were two to three times worse. A slower machine is
slower for both legs.

The collation is now declared at the one place that starts a server, so
the five other servers with the same exposure were fixed by the same
change rather than one at a time — and it is **checked** against a stated
expectation, not merely printed. Printing is where three of this
release's defects lived.

Your own two, in that note, are the same class and you wrote both into
the code rather than deleting them: an oracle that compared C against C
and saw nothing, and a run that reported "identical" because a
`2026-02-29` row failed the load and left both tables empty. **An empty
answer and a matching answer are the same bytes** — we hit that one this
round too, in a memory measurement that reported `0 MB` for both binaries
because a pattern matched no process. The corrected run prints the pid
and the row count beside the numbers, for the same reason your first
probe is now `count(*)`.

Four gates in this release gained the ability to see something they had
claimed to check. The sweep's control leg was printed and dropped for
five hundred rounds. Its `ORDER BY` cells were measuring the wire
transfer rather than the sort. Seventeen "we know this differs from
PostgreSQL" comments had no list and not one had been re-measured — of
the nine we re-ran, one no longer reproduced, one was stated backwards,
one was already closed, and one nobody had recorded at all.
