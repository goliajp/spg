## What moved

Our release gate times sorting shapes against PostgreSQL 18.4 on the
same box, both engines ordering bytes, 400,000 rows. Two releases ago
its worst cell was **6.12x** behind. At 7.38.20 it was 2.01x. At this
release:

| shape | vs PostgreSQL 18.4 |
|---|---|
| `ORDER BY <int>` | **0.71x** |
| `ORDER BY <int>, <int>` | **0.89x** |
| `ORDER BY <text>`, 26 distinct values | 1.24x |
| `ORDER BY <text>`, short distinct | 1.33x |
| `ORDER BY <text>`, long distinct | 1.44x |
| `ORDER BY <text> LIMIT 10` | 1.34x |

Sixty-four endpoint cells, no losses.

Three of the five changes are the in-memory sort: a later ORDER BY key
is now read only inside a run of rows that tie on the earlier one, a
second key no longer sends the whole sort to the general comparator,
and a top-N row that loses on its first eight bytes never has a sort
key built for it at all.

The fourth is the one worth your attention, because it decides which of
your queries the other three reach. **A sort larger than `work_mem`
spills**, and the spilled sorter is a separate implementation that had
none of this. It has it now:

    SELECT pad FROM t ORDER BY k, id   -- 50,000 rows, 200-byte column
    before   22.854-23.464 ms
    after    19.840-20.874 ms

PostgreSQL spills the same query — external merge, 10.8 MB of temp —
and answers in 19.4-36.2 ms on that box. So if your sorts are wide
enough or long enough to spill, this is the release that reaches them.

The fifth: **declaring a collation no longer costs the top-N shape
anything.** It was 4.16x the same query under `C`; it is now 1.01x, and
both are faster than either was.

## One correctness item

A sort that spilled could hand back rows that tie on the ORDER BY key in
a different order from the same sort done in memory. SQL does not
promise an order for ties, so no answer was wrong — but the same query
against the same data could return the same rows arranged two ways
depending on whether it fit in memory, which is not a difference anyone
should have to know about. Ties now come back in the order the rows
were read, on both paths.

If you have a query whose output order you have come to rely on WITHOUT
an ORDER BY that fully determines it, this release makes that order
stable where it was not. It does not make it guaranteed: the way to
guarantee it is still to name enough columns in ORDER BY.

## What we are not claiming

The numbers above are our gate's, on our box, against PostgreSQL 18.4
configured the way that gate configures it (`work_mem = 4MB` on both
sides, both ordering bytes). They are the shapes we test, not yours. If
you have a sort that matters and you want it in that panel, send us the
shape and the row count and it goes in — that is how the 200-byte
column and the top-N cell got there.
