# spg → sentori — 7.38.22, and one thing you should check

**Image:** `goliakk/spg:7.38.22`
**Manifest digest:** `sha256:2715e243c777fb968024366c39afd585edba85d20421acc5f6636b5dd3388f13`
**Battery:** nine-step prerelease green on the exclusive testbed;
drop-in acceptance 71/71 against the built image.

Two things in this release touch what your queries return. Neither is
something you reported; both are things we found by measuring our own
claims.

## A collation was reaching only one of our two sorts

We have two sort implementations. One of them ignored collations
entirely — it compared bytes whatever the collation said. The one it
ignored them in is the one a plain `SELECT … ORDER BY` takes.

    SELECT s FROM t ORDER BY s COLLATE "en_US.utf8"
    7.38.21 and every release before it   Banana, Cherry, apple, date
    PostgreSQL 18.4                       apple, Banana, Cherry, date

The same held with no `COLLATE` in the query, on a database that
DECLARED one: `datcollate` reported `en_US.utf8` and the rows came back
in byte order. So the catalogue said one thing and the answers did
another, and which you got depended on which internal path the query
took — a subquery honoured the collation, a plain select did not.

We checked this against the published images rather than reasoning from
the source: **7.38.6, 7.38.16, 7.38.18 and 7.38.21 all do it.**

**What to check on your side:** if any of your databases declares a
collation other than `C` — or if you have ever written `ORDER BY …
COLLATE` — those queries were sorting by bytes and are now sorting by
the collation. That is a change in row order for existing queries. It is
the order PostgreSQL gives, and it is the order your catalogue was
already claiming, but it IS a change from what 7.38.21 returned.

If you would rather keep byte order, `SPG_LC_COLLATE=C` on the server,
or an explicit `COLLATE "C"` on the key, both give exactly the old
answers.

## The image now collates like the image it replaces

`postgres:18` ships `LANG=en_US.utf8`. Ours shipped nothing, which fell
through to `C`, so moving from the standard PostgreSQL image to ours
silently changed row order. Ours now sets the same value.

**This reaches NEW databases only.** We verified that against running
images, not by reading code: a data directory created by 7.38.18, and
one created by 7.38.21, both keep the `C` they were created with when
opened by 7.38.22, with their row order unchanged. That is the same rule
`postgres:18` follows for the same variable.

So an existing deployment sees no change from the flip. A NEW database
created on 7.38.22 will collate by locale, as it would on PostgreSQL.

### What it costs — and the first number we gave you was for the wrong shape

We first wrote that it costs 164.8 ms under `C` against 232.5 ms under
`en_US.utf8`, 1.41x. That is true of the cell we measured, and that cell
sorts 400,000 rows entirely in memory. A sort that RETURNS its rows
spills to disk, takes a different code path inside us, and costs more.
We had no cell for it, which is why the first number was the one we had.

Measured since, inside the published 7.38.22 image, with an explicit
`COLLATE "C"` as the control so both legs run in the same window:

    SELECT s FROM t ORDER BY s        400,000 rows of 192-character text
    under COLLATE "C"                 273 ms   (256-315 over six pairs)
    under the image's own default     638 ms   (623-654)
                                               2.36x  (2.02-2.44)

The image's own default is `en_US.utf8` as of this release, so **this is
what a plain `ORDER BY` on a text column costs now, with nothing declared
on your side.** On 7.38.21 the same query was free — because it was
ignoring the collation, which is the defect above.

We have found why and fixed it: the two halves of that sort built their
keys differently, one of them not knowing a collation was in force, so
every comparison in the merge re-derived what the other half had already
established. Handing that half its collations took the same query to
1.3x; a second change — the test that decides whether a value is in the
alphabet a byte-ordering collation orders by bytes, which was walking
one byte at a time — took it the rest of the way. **The next release
measures 0.99x**, spread 0.96-1.08. Declaring a collation that orders
your data the way bytes do will cost nothing.

Against PostgreSQL 18.4 under the same locale we measured 234.2 ms to
its 360.4 ms, both engines agreeing row for row.

If this shape matters to you before that release lands, `SPG_LC_COLLATE=C`
on the server restores the old cost exactly, at the price of the old
byte order.

## Sorting, for the record

Sorting by a long text column that is not projected measured 308.9 ms
against PostgreSQL 18.4's 107.6 ms — 2.87x — and none of our panel cells
could see it, because every one of them projects what it orders by. It
is 109.8 ms now, 1.18x, and the panel has that cell.

Sixty-four endpoint cells, no losses.

## What we are not claiming

The timings are ours, on our testbed, against PostgreSQL 18.4 configured
the way our gate configures it — 400,000 rows, `work_mem = 4MB`, and
both sides stated where they collate differently. They are the shapes we
test, not yours. Send us a shape and a row count and it goes in the
panel; that is how the cell above got there.
