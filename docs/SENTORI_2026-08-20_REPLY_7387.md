## 1. What we did instead of fixing §3.1

Your §3.1 is the ninth defect filed against the same subsystem in
eight releases. Each of the previous eight was fixed the way you would
fix a bug: find the arm that is missing, add it. That is why there
were nine.

They were all one behaviour. Describe answers a statement's column
list from the schema, and when it met a select item it could not type
it returned an empty list — for the **whole statement**. Your row six
is the exact shape of it: `SELECT id, f_sql() FROM t`, where `id` is
an ordinary integer column of an ordinary table, and it disappears
because of what stands next to it. A data-modifying CTE, a subquery in
a select list, a top-level null test, ordered-set aggregates, a
set-returning function in FROM, and now a user-defined function — six
of the nine reached us through that one line, and the other three were
adjacent to it.

So 7.38.7 changes what an unknown costs. An item Describe cannot type
now contributes one loosely-typed column instead of erasing the
statement's shape. The UDF case is also fixed properly — the return
type is read from the declaration, at any depth, so `f_sql()`,
`f_arg(1)`, `f_sql() AS aliased` and `f_sql() + 1` all name and type
correctly — but if we had only done that, your tenth report would have
been the next expression we had not thought of.

Your observation about psql rendering `SELECT gi()` ragged was the
useful thread and it was right: the type on the wire was not the type
the executor used, because **Describe carried its own partial copy of
the naming rule** and the two had drifted. A bare `count(*)`
described as `?column?` while the row description said `count`. There
is now one rule, and Describe asks the same function the executor
does. Two gaps we found inside that shared rule are fixed there rather
than in one caller, which is also what closes your §3.2: a cast is
transparent to naming and supplies the target type's `typname` only
when the operand has none of its own, so `7::bigint` is `int8`,
`CAST(7 AS bigint)` is `int8`, `now()::date` is `now`, and `1+1` stays
`?column?`.

**A gate that would have caught all nine.** Every `Expr` variant now
has a statement that must describe a column. A second test reads the
AST's own source and fails when a variant appears that the list does
not mention — so the next expression we add cannot quietly have no
arm. We watched it fail before trusting it: it names six shapes with
no arm today, which are surviving on the fallback above rather than
erasing anything. Those six are ours to close and we know their names.

## 2. Your dump found three defects in an afternoon

You asked for `kill -9` mid-write against the `events` insert path and
the directory reopened by the next release's binary, with the 40
indexes watched. That is now a committed fixture in our release
battery — your dump, gzipped, in the repository rather than fetched
out of band, because a gate that is skipped by default is not a gate.
It restores, takes 200 acknowledged writes, dies by `SIGKILL`
mid-statement, reopens, and then compares each index-backed answer
against a sequential scan of the same predicate. There is no
expectation file to go stale, and an index that came back subtly wrong
fails where a row count cannot. It passed on this release, on two
different machines.

Getting it running found three things, none of which your suite would
have reached because they need your data:

**A `TEXT` body in a `jsonb` column killed the checkpoint thread.**
The encoder treated that pair as unreachable, on the reasoning that
the insert path had validated it — it had, under a looser rule. This
is the worst shape a defect can have: a background thread dies, writes
keep being acknowledged, and nothing reaches disk. Fixed, with the
round trip pinned.

**A scalar subquery returning a `uuid` refused to materialise.** The
list it consulted had grown one incident at a time and yours was not
on it. A type with a text input syntax now needs no entry at all —
`inet`, `macaddr`, `money` and the date/time family came along with
it.

**`pg_attribute.atttypid` was 0 for the network, money and text-search
types**, so anything reflecting on a schema containing them was told
nothing. Your dump has them; ours did not.

## 3. The performance harness — and what it says about us

`xbench/dropin-perf/run.sh`, with your shapes as its default profile.
It does what you said would decide anything: both databases as
containers on the same box, started the same way, seeded by the same
SQL, in the same run; legs interleaved at the cell level with the
starting leg rotating each round, because running all of A then all of
B puts one leg always second and the machine drifts underneath it;
a control leg of the reference image against **itself**, so the run
reports its own noise floor; and ranges that overlap printed as
`unresolved` rather than as a small win. Exit 2 is the harness being
broken and is not reachable from the same path as a clean run — we
took that convention from you.

A profile is a directory: `schema.sql`, and `shapes.tsv` with one
`name<TAB>SQL` per line. The one we shipped is our reading of your
description — single-row insert into a table carrying GIN
`jsonb_path_ops` and BRIN, and aggregates over a time window — and it
is a guess at your statements, not your statements. Replace it.

**We ran it before sending it. We lose.**

`goliakk/spg:7.38.7` vs `postgres:18-alpine`, same box, N=6, each
sample min-of-3, control clean on 7 of 8 cells:

| shape | SPG | PG 18 | |
|---|---|---|---|
| ingest: one row | 6.6-44.8 ms | 2.0-108.2 ms | unresolved |
| window: count over a day | 24.8-27.0 | 8.0-15.4 | **1.6× slower** |
| window: group by kind | 26.3-29.2 | 7.1-8.1 | **3.2×** |
| window: distinct seats | 40.7-45.4 | 14.0-21.2 | **1.9×** |
| jsonb: containment | 20.6-22.9 | 8.7-9.9 | **2.1×** |
| jsonb: containment in a window | 65.0-69.3 | 6.9-7.3 | **8.9×** |
| btree: project and kind | 0.19-0.24 | 0.21-0.30 | tie |
| dashboard: top versions | 35.2-36.2 | 5.1-6.6 | **5.4×** (control dirty here) |

A second box with a much worse noise floor put the 8.9× cell at 7.8×.
Two machines, two noise floors, same band.

**Two named causes, from the plans rather than from a guess.** For the
worst cell:

```
SPG    Aggregate
         -> Seq Scan on events
              Filter: (traits @> …) AND (received_at >= …) AND (received_at < …)

PG18   Finalize Aggregate -> Gather (Workers Planned: 2)
         -> Parallel Bitmap Heap Scan on events
              Recheck Cond: (received_at >= … AND received_at < …)
              Filter: (traits @> …)
              -> Bitmap Index Scan on events_time
```

1. **A range predicate on a BRIN-indexed timestamp does not drive an
   index scan for us.** We read all 200,000 rows; PG touches a
   fraction. Every window shape in that table is this one cause, and
   the plain one-day count states it cleanly: same predicate, no
   jsonb, still sequential.
2. **We have no intra-query parallelism.** The `jsonb: containment`
   row is the control for this — PG18 *also* scans sequentially for
   that predicate and still wins 2.1×, which is two workers and
   nothing else. So a ~2× floor sits under every large scan we run,
   before the planner is involved at all.

We are not going to price this in a letter. It is a decomposition
against PG's scan path, and it is the next version's work; you will
get the numbers when there are numbers rather than a plan. What we can
say now is that the `btree` row being a tie and the two jsonb rows
bracketing each other is the shape of a real result, not a harness
that is biased against us.

You said your performance gate stays at zero until you have measured.
Keep it there. We would rather you ran this against your own
statements and got a worse number than ours.
