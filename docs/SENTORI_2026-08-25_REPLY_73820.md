## 1. Your §2.1 — the CTAS command tag

Fixed, and the differential found four more forms while confirming the
one you named. Measured on PG 18.4, because the two that are **not**
`SELECT <n>` are the ones reasoning would have missed:

| statement | PostgreSQL 18.4 | SPG before |
|---|---|---|
| `CREATE TABLE t AS SELECT …` | `SELECT 3` | `CREATE TABLE` |
| `… WITH NO DATA` | **`CREATE TABLE AS`** | `CREATE TABLE` |
| `SELECT … INTO t` | `SELECT 3` | **syntax error** |
| `CREATE MATERIALIZED VIEW …` | `SELECT 3` | bare `CREATE` |
| `… MATERIALIZED VIEW … NO DATA` | **`CREATE MATERIALIZED VIEW`** | bare `CREATE` |

All five were wrong. The count was wrong too — the executor returned zero
for the materialised rows, so even a correct tag would have said `SELECT
0`.

**One of them had a test defending it.** The materialized-view case was
pinned as `CREATE`, under a comment reading *"a recorded delta (PG:
SELECT <n>)"* — the right answer and the wrong assertion in the same
breath. A divergence written down and then made the expected value is a
defect with a test protecting it, and this one survived because the note
read like a decision.

`SELECT … INTO` had never parsed at all, while a comment in our AST has
said since v7.38 that it and CTAS lower to the same node. Making it work
took three layers, and each was a classifier deciding *is this a read*
from the first word: the parser, the read/write dispatch, and the tag.
`CREATE TABLE … AS` was right at all three, so the two spellings of one
statement disagreed about all three.

## 2. Your §2.2 — the UDF result type

Fixed. You were right that the executor was never confused; only the type
travelling in the `RowDescription` was. `SELECT 7::bigint, f_sql()` now
right-aligns both cells.

The cause is worth telling you because it is the same shape as §1: the
projection called the catalog-**less** type walker, and the user-function
arm is the one arm of that walker that needs a catalog. `Describe` had
been given one in v7.38.7 and the projection had not, so the two
disagreed about the same expression — which is the disagreement you
reported one round earlier in a different place.

**The first pin we wrote for it did not work.** We wrote a corpus file
with `query I`, believing the runner's `I` checks the column's type. The
negative control — put the old call back — left it green: the runner
compares rendered values and never asks the schema, so that defect could
not be expressed there at all. Asserting the column type directly, the
same negative control reads `left: [Text] right: [BigInt]`.

## 3. Your §3 — `CREATE DATABASE … LC_COLLATE`

**`pg_database` now lists every name the server answers to**, so `dd` is
in the catalogue that `psql \l`, a migration tool's "does this database
exist" and a backup script all read.

Your second point cannot be fixed while SPG serves one database: a
statement naming `dd` does change how `d` compares text, and under
PostgreSQL's model nothing a `CREATE DATABASE` does can reach an existing
one. What can be fixed is the silence, and it is: the statement now warns
that the names are aliases onto one database and that the collation
applies here too. You are right that the dangerous case — indexes built
under one collation, probed under another — was already guarded; that
guard is why you could not make it drop rows.

The first version of our fix recorded the *keyword*: `pg_database`
listed a database called `database`.

**And your accident found something we would not have.** You wrote up the
wreckage rather than the finding, and the finding came out of the
wreckage. Two hours after reading it we made the same class of mistake in
our own release gate — §6.

## 4. What was behind them

- **`SELECT 1::xid8` returned `1`** where PostgreSQL answers `cannot cast
  type integer to xid8`. **Us accepting what PostgreSQL rejects is the
  worse direction**: code PostgreSQL would have stopped runs here, and
  the difference surfaces somewhere else, later. Nobody had recorded it;
  it surfaced because a comment two lines above it was being re-measured.

- **`nextval`, `setval`, `pg_advisory_*` and `lo_*` all returned
  `?column?`** where PostgreSQL names the column after the function. They
  are evaluated by a pass that replaces the call with the literal it
  produced, and a literal has no name to figure out. An ORM reading
  column names got `?column?` for every one.

- **`pg_advisory_unlock` did not warn** when you do not hold the lock.

- **Starting the server cost the size of a directory it does not own.**
  It swept the whole system temp directory at every start; on our machine
  that had reached 61,708 entries and 30 GB, and one `readdir` took **95
  seconds**. Every server our own tests spawned waited a minute and a
  half before it could listen — and the failures read exactly like a busy
  machine, which is what we had been calling them.

## 5. Performance

### Your three shapes, taken apart

We took them apart stage by stage rather than looking for something to
tune. Two of the three are closed in this release; what fell out of the
first was not a tuning matter at all.

Your `events` table carries `(project_id, kind)`. Your dashboard filters
on `project_id` alone. On 200,000 rows, on an idle box, interleaved,
each of these predicates matching **nothing at all**:

| predicate | before | after | PostgreSQL 18 |
|---|---:|---:|---:|
| `project_id = 99` | 3.415 ms | **0.195** | 0.207 |
| `project_id > 90` | 3.282 | **0.166** | 0.214 |
| `project_id BETWEEN 90 AND 99` | 6.395 | **0.191** | 0.204 |
| `project_id IN (98, 99)` | 3.069 | **0.198** | 0.212 |

Read the "before" column against the fact that these match no rows. A
query returning nothing cost what a query returning a quarter of the
table costs, because that is what it did — it read every row. Your
index was there. We could not see it.

The reason is narrow and it is ours. A composite index keys tuples, and
asking one a question shaped like a single column gets an empty answer
that looks exactly like "no rows matched" — a mistake we have made twice
before and now guard against by refusing such an index outright. That
refusal is what every single-predicate path hit. The walk it needed
already existed, already correct, and had since v7.38.1 — but it lived
where two conditions meet, so a `WHERE` with **one** condition never
reached it. A composite index answered `project_id = 3 AND kind =
'click'` in 0.19 ms and `project_id = 3` by reading the table.

Your dashboard query, eight alternating rounds: **9.77–11.52 ms before,
6.66–9.01 after**, against PostgreSQL's 3.75–3.99.

One more of the same kind, found while measuring the above: `a = 1 OR a
= 2` read the whole table while `a IN (1, 2)` — the same question — took
a descent. 6.426 ms against 0.194. Fixed in the same release.

### Your containment filter

`traits @> '{…}'` rides the GIN index, so what costs is the recheck on
each row the index returns. We had already stopped building a document
for the left side of that comparison; we were still building one for the
**right** — the constant in your own WHERE clause, rebuilt for every
matched row, plus one more parse per value found on the left.

    traits @> '{"plan":"pro","country":"jp"}'   8.421 ms → 5.068   PG 4.236
    the same filter matching nothing            0.607     0.599        0.753

Read the second line. With nothing to recheck we were already faster
than PostgreSQL, which is what said the whole gap was per-matched-row.

Three of your `?`-style operators had the same defect in a worse form:
they parsed the entire document — every key, every value — to answer
whether ONE key was present. `traits ? 'plan'` cost 46.599 ms where
`traits->>'plan'`, which finds the same key *and copies the value out*,
cost 14.137.

### Where the three shapes stand now

Your harness against the shipped image, on an idle machine, three
consecutive runs, the control leg clean in all three:

| your shape | v7.38.18 | v7.38.20 |
|---|---|---|
| `ingest: one row` | 61.3% slower | **no measurable difference, in all three runs** |
| `jsonb: containment` | 64.7% slower | **3.2% slower / no difference / 10.3% slower** |
| `dashboard: top versions` | 113.8% slower | 68–79% slower |

Two of the three are closed. The third is not, and the rest of this
section is what we know about it.

The same runs put us **ahead** on five of the eight cells:

| | |
|---|---|
| `window: count over a day` | 1.93–2.26x faster |
| `window: distinct seats` | 1.01–1.24x faster |
| `jsonb: containment in a window` | 1.08–1.16x faster |
| `window: group by kind` | 1.10–1.16x faster |
| `btree: project and kind` | 1.04x faster |

**`ingest: one row`.** Your `events.id` is a `bigserial`. We give it the
next value by taking the table's current maximum and adding one, which
means reading the table. PostgreSQL reads a counter that knows nothing
about the table. So:

| rows in the table | us | PostgreSQL 18 |
|---|---:|---:|
| 1,000 | 1.831 ms | 1.245 |
| 10,000 | 1.814 | 1.289 |
| 50,000 | 2.703 | 1.386 |
| 200,000 | 3.666 | 1.375 |

Theirs was flat. Ours was not, and **your ingest got slower as the table
grew** — the shape of thing you find months in, as "it used to be fast".

It is not the indexes, which were the obvious suspects and were wrong:
dropping the GIN, the BRIN and the composite one at a time changed
nothing measurable, while PostgreSQL's own GIN costs it 0.5 ms of its
1.7. What separated it was adding one column kind at a time to a
200,000-row table — `bigserial PRIMARY KEY` jumped from 1.374 ms to
4.326 and nothing else moved — and then timing the sequence alone, which
costs 0.187 ms called directly and added 1.9 when it filled a column.

**Fixed in this release.** A B-tree on the column already holds those
values in order, so its largest key is a descent rather than a walk. On
your 200,000-row shape: **3.666 ms → 1.106, against PostgreSQL's 1.075**,
and flat. Your `id` is a `PRIMARY KEY`, so the index was there the whole
time.

There is a second half to it we have not resolved, and it is a judgement
call rather than a bug. After a row supplies its own id — three inserts
with an explicit `50` in the middle — PostgreSQL gives `1, 2, 50` and we
give `1, 50, 51`. Their counter will eventually count up to 50 and the
insert that lands there will fail on the primary key. Ours never hands
out a value the table already holds. A real counter with a floor at the
table's maximum closes both the scaling above and the divergence, and
that is where we are going; it is written down as RD-12 rather than
quietly left as "ours is fine".

**`dashboard: top versions` — the one still open.** The index finding
above took it from 9.8 ms to 7.0–7.5 against PostgreSQL's 3.8–4.0. What is left is not the scan and
not the index — it is what a row costs us on the way through, about
1.7x theirs on a plain filtered count with no index in play (46 ns a row
against 27, measured across three table sizes). `traits->>'version'` is
part of it and is actually our *narrowest* gap of the three
(168 ns a row against 112). That one needs a profiler rather than
another hypothesis, and it is the next thing we take apart.



### A regression we shipped in v7.38.18

Found by the same audit. It is not one of your three.

`WHERE kind = 'click'` over 200,000 rows, interleaved on one box:

| | |
|---|---|
| database collation `C` | 2.2–3.1 ms |
| database collation `en_US.UTF-8` | **58.3–76.2 ms** |
| PostgreSQL 18.4 | 1.5–4.4 ms |

Twenty-six times our own byte path, thirty times PostgreSQL, on the most
ordinary predicate there is. Two causes, both work done per row that
belongs once per query: a folding step that copied each side into a fresh
string and left it exactly as it found it, and a call that parsed the
locale and built a whole ICU collator **on every comparison**.

After: text equality 2.6 ms, level with PostgreSQL. Ordering went 62.5 →
15.3, and a collated `ORDER BY` 328 → 264 ms against PostgreSQL's 158 —
still 1.67x behind, named rather than left out. That last one cost 18 MB
of peak memory for its 20 % of time, and we would rather give you both
numbers than the flattering one.

**This does not change your figures**, and we checked rather than
assumed: our image starts a database under `C`, so none of it applies to
a deployment running the stock image. What moved your three shapes is
the index finding above.

**Which raises something you should know, and it touches your gate 2
conclusion directly.** `postgres:18` starts under `en_US.utf8` and sorts
`apple, Bob, Zebra`; our image starts under `C` and sorts `Bob, Zebra,
apple`. A team moving off the standard PostgreSQL image gets a different
row order from us, silently.

We have not flipped our default, and when we wrote the paragraph above
the reason was a trade: doing it would hand every deployment the ordering
cost. **That reason is gone.** Closing the ordering gap turned out to be
worth doing on its own, and we did it before finishing this letter.

Under many collations — not all — the letters and digits `a`–`z` and
`0`–`9` sort in exactly byte order, so the collator need not be asked
about them at all. Which collations, we measured rather than assumed:
over all 839,160 ordered pairs of two-character strings from that
alphabet, English, German, French, Swedish and Turkish agree with bytes
exactly, while Czech disagrees 198 times (`ch` is a single letter,
sorting after `h`), Estonian 7,992 (`z` sorts between `s` and `t`),
Lithuanian 20,609, Danish 925, Hungarian 18. It is an allowlist, and the
test beside it re-derives the whole list in process — including that the
five in the second column must fail, because an allowlist nothing falls
outside is not a check.

On 400,000 rows of 192-character text, both engines under `en_US.utf8`:

| | before | after | PostgreSQL 18 |
|---|---:|---:|---:|
| `ORDER BY … LIMIT 10` | 1357.5 ms | **43.2** | 11.4 |
| `ORDER BY …` (full sort) | 1706.5 | **395.6** | 415.9 |
| short text, `LIMIT 10` | 114.0 | **14.7** | 21.9 |
| short text, full sort | 446.1 | **211.0** | 502.4 |

Three of those four now beat PostgreSQL. A value outside the alphabet —
anything with a space, a capital or an accent in it — still pays full
ICU, correctly and unimproved, and a mixed column pays it only for the
values that need it.

So the cost argument for keeping `C` no longer holds.

**But there is a second reason, and it is yours.** Your divergence note
found that the eight collation-sensitive probes differ between
`postgres:18` and `postgres:18-alpine` — that the ordering of your
project and version listings already depends on which Postgres a
deployment runs, and that your documentation does not say so. If we
flipped our image default, we would make that change *for* your
`docker-compose` users without their asking. On names shaped like yours:

```
SPG under C            Beacon, Zephyr, _internal, apollo, atlas
SPG under en_US.utf8   apollo, atlas, Beacon, _internal, Zephyr
PostgreSQL 18 (glibc)  apollo, atlas, Beacon, _internal, Zephyr
```

We match PostgreSQL exactly under a locale and differ from it under `C`,
which is the whole of the question. When we do flip it, it will be a
release that says so in its first line, not a default that moves under
you. If you would rather have the PostgreSQL ordering before then,
`SPG_LC_COLLATE=en_US.utf8` on the container does it today — and on the
data you described the cost lands on `ORDER BY p.name` and `ORDER BY
r.name`, which is where you already said the exposure is.

**As it stands you are unaffected either way** — `postgres:18-alpine`,
which you run, declares `en_US.utf8` and sorts by bytes anyway, because
musl carries no locale data. Your gate 2 result holds: what we do matches
what you deploy.

The harness is at `xbench/dropin-perf/`, self-contained, with a README
written for someone who does not have our checkout. It needs `docker`,
`psql`, `awk` and the POSIX text tools — we said "three commands" first
and then listed what the script actually calls, which was ten.

## 6. What we got wrong this round

Your §7 described running a capability test in the same container as a
measurement. We did the same class of thing, in our release gate, and it
had been true for months.

**Our testbed exports `LANG=en_US.UTF-8`.** Every server our suite starts
inherited it, so the perf sweep's baseline leg — the one every comment
calls the `C` leg — had been running under a locale collation the whole
time. Which means the locale-collation panel we added *in this same
release, to catch exactly the regression in §5*, was comparing
`en_US` against `en_US` and reporting no losses. **An instrument that
cannot fail is not a check**, and this one was added by the same hand, in
the same version, two hours earlier.

It surfaced because a panel went red with numbers that made no sense
beside the local ones: PostgreSQL's times were nearly identical on both
machines while ours were two to three times worse. A slower machine is
slower for both legs.

The collation is now declared at the one place that starts a server, so
the five other servers with the same exposure were fixed by the same
change rather than one at a time — and it is **checked** against a stated
expectation, not merely printed. Printing is where three of this
release's defects lived.

Your own two, in that note, are the same class and you wrote both into
the code rather than deleting them: an oracle that compared C against C
and saw nothing, and a run that reported "identical" because a
`2026-02-29` row failed the load and left both tables empty. **An empty
answer and a matching answer are the same bytes** — we hit that one this
round too, in a memory measurement that reported `0 MB` for both binaries
because a pattern matched no process. The corrected run prints the pid
and the row count beside the numbers, for the same reason your first
probe is now `count(*)`.

Four gates in this release gained the ability to see something they had
claimed to check. The sweep's control leg was printed and dropped for
five hundred rounds. Its `ORDER BY` cells were measuring the wire
transfer rather than the sort. Seventeen "we know this differs from
PostgreSQL" comments had no list and not one had been re-measured — of
the nine we re-ran, one no longer reproduced, one was stated backwards,
one was already closed, and one nobody had recorded at all.

## Two more things this build carries

**A sort we thought was 2.9x behind PostgreSQL was 6.1x, and is now
1.5x.** Not a new regression: our own gate had been flattering it. It
rebuilds its fixture every run and never analysed it, so PostgreSQL
planned a serial sort from missing statistics some runs and a parallel
one others — 117 ms against 62 ms for the same query, deciding the
verdict for the whole run. The same binary scored 2.81x and 5.76x on
different days. Both legs are analysed before anything is timed now,
and both legs' spreads are printed rather than a bare minimum each.

The number that uncovered is worse than the one it replaced, and the
work that followed is what the version is mostly made of:

| shape, 400,000 rows, both engines ordering bytes | before | after |
|---|---:|---:|
| `ORDER BY` an integer | 0.99x | **0.79x** |
| `ORDER BY` short text | 2.93x | **1.42x** |
| `ORDER BY` long distinct text | **6.12x** | **1.53x** |

Three things, each found by profiling the one before it: the sort key
was a copy of a column the output already carried; the byte comparison
was a library call made ~7.4 M times; and the rows themselves were what
got sorted, 48 bytes moved n·log n times with three pointer hops per
comparison. It now sorts an eight-byte key beside a row number.

Declaring a collation used to cost up to 4.09x on those shapes and now
costs 1.00x–1.26x.

**And one operational hazard, which we would flag even if you never hit
it.** A database created under `C`, restarted from the same data
directory with a different `LC_COLLATE` in the environment, silently
adopted the new collation and reordered every text column. The guard
against that already existed — a collation cannot change once the
database has tables — but it ran before the WAL was replayed, so a
server killed without checkpointing (every crash, every plain `kill`)
came up with an empty catalog, took the environment's answer, and then
replayed the rows in under it. `initdb` writes the collation into the
cluster and a later `LANG` does not touch it; ours now behaves the same
way, and says so loudly when it refuses.
