## 1. We ran your harness on ourselves first, and we lost

Two things about that number before the fixes.

**It is not the harness.** The control leg was clean on the cells it

## 2. What was actually wrong

Three predictions were made from reading our own code and all three
were refuted by measurement. The refutations are the useful part, so
they are in
`docs/PERF-FINDING-2026-08-20-sentori-shapes.md` in full.

**A timestamp comparison cost 52 ns a row against an integer
comparison's 22.** Not an index choice, not the constant fold, not a
compiled-lane miss — we checked each with a discriminator that would
have shown it. What was left is that our fast comparison path had arms
for integers, text and booleans and none for temporal types, and that a
timestamp literal reached the row loop as TEXT whatever the spelling,
because the AST had no variant that could hold a decoded one. So every
row walked a guard chain and then parsed the same string again. Now
21.6 ns, parity with an integer comparison. `now()::date`, `EXPLAIN`
output and dumps print exactly as before — verified byte for byte
against a 7.38.7 server.

**A jsonb field access cost 398 ns a row against PG's 11.** `->>`
parsed the entire document into a tree solely to validate it, threw the
tree away, and then found the key by scanning the source text, which is
the part that does the work. And the key comparison ran the parser over
every key it walked past, allocating a string for each, to answer what
is usually a byte comparison. Now 173 ns. PG is at 7.5 to 12, so this
is a step and not the end of it — the representation itself is next.

**The same query in a different written order cost 4.7 times as much.**

```
WHERE traits @> '{"plan":"pro"}' AND received_at >= … AND received_at < …   40.0 ms
WHERE received_at >= … AND received_at < … AND traits @> '{"plan":"pro"}'    8.5 ms
```

PG answers both alike because it orders quals by cost. We evaluated
them as typed, and which one a person types first is habit. Both
spellings now measure 8.5.

That last one took three attempts and two of them were wrong, which is
worth telling you because it is the same failure mode as reading a
green suite: done in the AST it won 4.7x and made every indexed shape
slower, because reordering the tree before the planner reads it changes
which index it picks. Done one layer lower it still cost two shapes it
does not even reorder 17% and 20% — a tax that scaled with row count
for a function that runs once per query, which is what a code-layout
effect looks like and not what work looks like. It ships in the third
placement, with the negative controls that separate the three recorded.

## 3. A defect your dump found, which is why the boundary moved

`INSERT INTO t VALUES ('{bad')` into a `jsonb` column was **accepted**.
PG18 answers `invalid input syntax for type json`. We stored the raw
text, and every later read of that row raised instead — in 7.38.7 one
of those reads was on the checkpoint thread, where writes keep being
acknowledged while nothing reaches disk. Our own coercion said so in
its comment: *"no structural validation — the responsibility for valid
JSON lies with the producer."*

Validation now happens where PG puts it, at the column boundary, with
PG's message. And that guarantee is exactly what the accessors above
were paying for on every row: with the boundary enforced, a stored
jsonb value is valid by construction, so `->>` no longer has to prove
it. A text operand — which PG has no operator for at all — is still
checked, because it has passed through no boundary.

**This changes behaviour**: a statement that inserted invalid JSON into
a json/jsonb column and succeeded will now raise. If anything in
Sentori relies on that, it was storing a value nothing could read.

| jsonb: containment in a window | 52.5 | **8.5** | 4.7 |

Two shapes ahead of PG, most of the rest within 1.3x. The one that has
barely moved is bare containment, and we know why: `@>` parses both
documents on every row, including the constant on the right — 200,000
parses of the same small literal for one query. That and the
representation are the next campaign, and they are written up rather
than promised.

**The profile is our guess at your statements, not your statements.**
`xbench/dropin-perf/profiles/sentori/` is a directory with a
`schema.sql` and a `shapes.tsv` of `name<TAB>SQL` lines. Replace it. If
your numbers are worse than ours we would rather have yours.

Three things the harness learned the hard way while being built, in
case you hit them: psql may itself be a container wrapper, in which
case `127.0.0.1` is not the host (`HOST_ADDR=host.docker.internal`); a
host path passed to `-f` is not a path such a psql can open, and the
failure reads as a bad schema; and it inherits stdin, so it swallows
the rest of the shape list on the first shape — which produced a run
that measured one cell of eight and printed a complete-looking table.
The list is read on a separate descriptor now and the run refuses to
report fewer cells than the profile lists.
