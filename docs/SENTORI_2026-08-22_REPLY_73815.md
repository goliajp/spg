## 1. A join could return nothing at all

On a case-insensitive text column — the MySQL default — `a JOIN b ON
a.s = b.s` returned **no rows** where MySQL 9.7.1 returns every one.

An empty result is the worst shape this class of bug can take. It reads
as "there is no matching data" rather than as an error, so nothing
raises, nothing logs, and nobody files a report. If any of your MySQL
schemas join on text, this one was silently costing you rows.

Two independent causes, and the second is why the first fix did not
work:

- A join rebuilds its column descriptions, and the rebuild carried the
  collation's *name* but not the collation itself. The field's default
  is "byte-wise", which the rest of the engine reads as *deliberately*
  byte-wise — so a lost declaration presented as an explicit one.
- An equality in `ON` is lifted into a **hash key**, and a key is
  hashed rather than compared. The fold has to happen when the key is
  built or it does not happen at all: `'a'` and `'A'` land in different
  buckets and the rows never meet. This is why three earlier fixes to
  the comparator changed nothing.

The same equality reached five ways — `JOIN … ON`, a cross join with
`WHERE`, `EXISTS`, `IN (subquery)`, and against a literal — now gives
one answer. It did not before: the shape of the predicate decided it.

## 2. Six more places, and the shape behind all of them

`DISTINCT` over a window, over `unnest`, over `generate_series`, over
`jsonb_each_text`, over a derived table, and over a `GROUP BY` result
all folded text regardless of what the column declared. So did `UNION`,
`INTERSECT` and `EXCEPT`. So did any comparison where the column was
wrapped in a function — `GREATEST(s,'A') = 'A'` lost a byte-wise
column's declaration at the first call. And `CASE x WHEN v` compared
bytes in one of its two implementations and folded in the other, so the
answer depended on whether the expression happened to compile.

Behind every one of them is one shape. Twenty-one places in this engine
build an output column from an input column, and they had **three
different ideas** of which attributes to carry: six copied three of
them, ten copied two, five copied none. Not one copied the collation.

That shape has now cost five separate defects over the project's life.
It is one function as of this release, with a test that does not check a
list of fields — a list is exactly what goes stale — but sets every
attribute away from its default, re-derives, and compares the whole
thing. The next attribute someone forgets fails there instead of in your
query.

## 3. What we corrected in our own understanding

Two things we believed and have now measured otherwise. Both ran against
us, which is why they are here.

**Our `EXPLAIN` was lying about indexes.** A jsonb containment that
really did use its GIN index printed `Seq Scan`. We found this because
an internal review read those plans and concluded no GIN index is ever
used — which would have been alarming and was false. Timed at 10,000
rows against 100,000 — twice, on two builds — the containment is flat
(0.005 → 0.003 ms) where a genuine sequential scan over the same table
is linear (0.114 → 1.123 ms). The index was working the whole time.

If you have ever looked at an SPG plan and concluded an index was not
being used, that conclusion may have been ours, not yours. The plan now
names the index it uses. A full-text `@@` match still prints `Seq Scan`
and still uses its index; that half is not fixed and we would rather say
so than let you find it.

**A temporary object said it lived in `public`.** Temporary tables,
views and sequences have been correctly session-scoped for many
releases — this was never a lifetime bug — but the catalog reported them
in `public`, so a schema-diff or migration tool had no way to tell a
temporary object from a permanent one. They report `pg_temp_N` now, as
PostgreSQL does.

## 4. Also fixed

`INSERT … SELECT` could not populate a `tsvector` column — the ordinary
way to backfill full-text search from existing rows. Worse than the
refusal was its advice: it told you to add an explicit cast, and adding
one changed nothing, because the value already had the target type.

## 4b. One number worth having

The `SELECT DISTINCT … ORDER BY` shape our 7.38.13 letter listed as a
standing loss is now **ahead of PostgreSQL 18** over the wire, in this
release's own gate: 87.9–94.5 ms against 114.9–120.8 ms at 400,000 rows,
ranges that do not overlap. It had flickered across three releases, each
of which spent a round proving it was not a regression without once taking
it apart.

## 5. Still open on our side

- **An index on an expression is accepted and never used.** `CREATE
  INDEX ON t (lower(s))` builds and the query answers correctly, but
  nothing ever selects it: the index is *inert*. The same query with and
  without it runs within one percent of itself at both 10,000 and
  100,000 rows, and the write side pays nothing either.

  We owe you a correction on our own arithmetic here. An earlier reading
  of ours had this index making queries several times *slower* than
  having none. That was two different predicates being compared, not one
  predicate with and without an index — `lower(s) = …` is simply dearer
  per row than the integer comparison it was measured against. The index
  costs nothing. It just does not help, which is the real complaint:
  this is the standard spelling for a functional index and for
  PostgreSQL's full-text indexing.

- **A UNIQUE index on an expression enforces by rescanning.** This one
  we found while checking the above, and it is the sharper edge:
  `CREATE UNIQUE INDEX ON t (lower(email))` does reject duplicates
  correctly — byte-for-byte PostgreSQL's answer — but it re-reads the
  table on every insert to do it. Measured, one insert: **0.43 ms at
  2,000 rows, 3.9 ms at 20,000**, growing with the table rather than
  staying flat. A plain unique index on a column does not do this. If
  you have a case-insensitive uniqueness rule expressed this way, its
  cost is rising with your data.

  Both are the same missing piece — expression keys the storage layer
  can look up — and both are next.

- **MySQL warning diagnostics.** Non-strict `sql_mode` bends values the
  way MariaDB does — that half is correct and byte-for-byte matched —
  but `SHOW WARNINGS` and `@@warning_count` are missing, so an
  application cannot discover that a value was bent. Recording warnings
  needs machinery the coercion path does not have today.
- **The three jsonb rows on your profile**, unchanged and unchanged on
  purpose: dispatch-bound rather than representation-bound, three
  attacks measured and discarded.

## 6. Nothing to change on your side

No configuration, no query rewrite, no new index. If you have MySQL
text joins, they will start returning rows they should always have
returned — that is the one behaviour change to expect, and it is the
point of the release.
