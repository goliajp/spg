# spg 7.38.6 → 7.38.18 — what changed, and what to re-check

**You are on `7.38.6`. The current release is `7.38.18`.**

| | |
|---|---|
| Image | `goliakk/spg:7.38.18` |
| Manifest digest | `sha256:PENDING` |
| Crates | 7.38.18 on crates.io (13) |
| Releases in between | ten published (7.38.9 and 7.38.14 were tagged and never published) |

This is not a feature list. Twelve releases separate you from current,
and **most of what happened in them was us finding wrong answers we had
been giving you**. So this document is organised around the question you
actually need answered: *what have I been getting wrong since 7.38.6, and
how do I tell?*

Section 1 is the queries whose answers may have been wrong on your build.
Section 2 is what to do about it. Section 3 is the upgrade itself.
Everything else is after that.

---

## 1. Answers that were wrong on 7.38.6

Every number below is measured against the engine we stand in for —
PostgreSQL 18.4 or MySQL 9.7.2 — not reasoned out.

**And we checked them on your build, not on our changelog.** We started
the published `goliakk/spg:7.38.6` image and ran these queries through
its MySQL wire. Confirmed there, with a `SELECT 1` and a row count
first so a broken probe could not pose as a finding:

| on the real 7.38.6 image | it gave | MySQL 9.7.2 gives |
|---|---|---|
| `a JOIN b ON a.s = b.s` (`'alpha'`/`'ALPHA'`) | **0 rows** | 2 |
| the same, with an index on both sides | **0 rows** | 2 |
| `WHERE s = 'ALPHA'`, no index | 1 | 1 |
| `WHERE s = 'ALPHA'`, **with an index** | **no rows** | 1 |
| `SELECT 'a' = 'a  '` | true | false |

### 1.1 If you use the MySQL wire, text comparisons were wrong in several shapes

MySQL's default collation folds case. Ours did too — in some code paths
and not others, and which path a query took depended on how it was
written.

| shape | MySQL says | 7.38.6 gave |
|---|---|---|
| `a JOIN b ON a.s = b.s` over `'alpha'`/`'ALPHA'` | both rows | **no rows**, index or not |
| the same join written `ON (a.s = b.s OR FALSE)` | the same rows as above | a **different** answer from the line above |
| `SELECT DISTINCT s` / `GROUP BY s` | folded | not folded, in six places |
| `UNION` / `INTERSECT` / `EXCEPT` | folded | not folded |
| `WHERE lower(s) = 'x'` | folded | folded only if `lower()` was not there |
| `CASE x WHEN v` | folded | folded in one implementation, bytes in the other |
| `ORDER BY s`, `MIN(s)` on a `COLLATE utf8mb4_bin` column | byte order | folded anyway |

Read the first two lines together: the same join, written two ways,
gave two different answers. That is the shape of this whole class —
which code path a query took decided whether the collation was
consulted, so the answer depended on the spelling.

**An empty result set is the worst of these.** It reads as "there is no
matching data" rather than as an error, so nothing alerts and the answer
looks like a fact about your data.

### 1.2 Adding an index changed the answer — including to nothing

This one is independent of how the query is written. On the MySQL wire,
with an index present on a text column:

| | MySQL says | 7.38.6 gave |
|---|---|---|
| `WHERE s = 'ALPHA'` | 1 | **no rows** |
| `WHERE s IN ('ALPHA','BETA')` | 1,2 | **no rows** |
| `WHERE s BETWEEN 'ALPHA' AND 'DELTA'` | 1,2,4 | 2 |
| `ORDER BY s LIMIT 2` | 1,2 | the wrong two rows |
| `a JOIN b ON a.s = b.s` | both pairs | **no rows** |

on `TEXT`, `VARCHAR` and `CHAR` alike. The same queries were correct with
no index — we confirmed both halves on your image above. **If you added
an index to a text column at any point while on 7.38.6, queries against
that column may have been returning less than they should.** The join in
§1.1 is the exception: it was empty either way on your build, because
joins did not consult the collation at all until 7.38.14.

`CHAR(n)` was also wrong without any index: `IN`, `>=` and `BETWEEN` kept
both the case and the trailing padding.

**7.38.18 found one more of these, and this one is not MySQL-only.** On
any wire, in any dialect:

```sql
CREATE TABLE ix (id INT PRIMARY KEY, s TEXT);
INSERT INTO ix VALUES (7, 'Row7');
CREATE INDEX ix_lower ON ix ((lower(s)));   -- an expression index
SELECT * FROM ix WHERE s = 'Row7';          -- 7.38.6: no rows
```

The lookup for "is there an index on column `s`" returned the
*expression* index built over `lower(s)`, and then probed it with the
un-lowered value. Nothing matches, and the answer is an empty result
rather than an error. It needs a column and an expression index over
that same column to appear, and it is silent when it does. This was
present in every release including 7.38.6, and is fixed in 7.38.18.

If you have any expression index — `lower(email)`, `date_trunc(...)`,
`(a || b)` — the §2 checks are worth running against the columns it
covers.

### 1.3 Trailing spaces were treated as insignificant

`'alpha'` and `'alpha  '` were the same value to a comparison, a
`DISTINCT`, a `GROUP BY` and an `IN` list. MySQL 9.7 says they are two
values. `SELECT DISTINCT s` and `count(DISTINCT s)` disagreed with each
other in the same session.

The cause is worth telling you exactly, because it was not carelessness.
The rule had a comment saying where it came from: *"measured on MariaDB
11"*. That measurement was right — about MariaDB, whose default
collation ignores trailing spaces. We advertise MySQL 8.0 on the wire,
and MySQL 8.0's default does not. **We had calibrated against the engine
we do not claim to be.**

7.38.17 fixed the default. **7.38.18 fixed the rest of it**, and the
shape of the remaining bug is worth a sentence: whether trailing spaces
count is decided by the collation's *name*, not by the column's type or
by any flag we carried. We read the name to decide case-folding and
never to decide padding, so `utf8mb4_bin` and `utf8mb4_general_ci` — the
names a MariaDB or older-MySQL dump writes — still gave the wrong answer
while the default gave the right one.

`utf8mb4_bin` is the one to stare at: it is byte-wise **and** pads, in
both engines. "Compares byte-wise" and "trailing spaces count" are
different questions, and we had one field answering both. The rule is
now measured rather than reasoned: over all 838 collations the two
oracles list — 286 on MySQL 9.7.2, 552 on MariaDB 12.3.2 — `NO PAD`
holds exactly when the name is `binary`, contains `_0900_`, or contains
`nopad`, with zero counter-examples on either engine.

### 1.4 A `json` / `jsonb` column accepted text that was not JSON

`INSERT INTO t (doc) VALUES ('not json')` succeeded on 7.38.6. It is
rejected now, as PostgreSQL rejects it. **If you have a jsonb column
that any code path writes without validating, it may contain values that
are not documents.** §2 has a query to find them.

### 1.5 Full-text and expression indexes

- `CREATE INDEX ON t (lower(s))` built, and nothing ever used it. It
  cost writes (an insert ran 1.9× a table with no index) and returned
  nothing for reads. It now answers: 0.004 ms against 7.7 ms for the
  scan at 100,000 rows.
- `CREATE UNIQUE INDEX ON t (lower(email))` enforced correctly but by
  re-reading the whole table on every insert — 0.43 ms per insert at
  2,000 rows, **3.9 ms at 20,000**, growing with your data. Now 6.0 µs
  at both.
- PostgreSQL's ordinary full-text spelling —
  `USING gin (to_tsvector('english', title || ' ' || body))` — was
  **refused outright**, so a schema using it did not load. So were
  `coalesce(...)` and `(meta -> 'tags')`. All three work now.
- The one full-text spelling that did work, `to_tsvector('english',
  body)` on a bare column, built the index with the wrong tokeniser and
  then **returned no rows**: it stored `lazy` while the query asked for
  the English stem `lazi`.

### 1.6 Client-side: prepared statements and `Describe`

If your driver uses prepared statements (sqlx, JDBC, most pooled
clients), 7.38.6 had a `Describe` that erased a whole statement's
column metadata when one item in the select list was unfamiliar — a
user-defined function, a scalar subquery returning `uuid`, a `money` or
network-typed column. The symptom is a client that reports "no
columns" or the wrong types for a query that runs correctly by hand.

## 2. What to re-check on your data

Nothing here needs our help to run. These are the checks we would run if
it were our database.

**a. jsonb columns that may hold non-documents** (§1.4). For each
`json` / `jsonb` column:

```sql
SELECT count(*) FROM your_table WHERE your_json_column IS NOT JSON;
```

Zero is the answer you want. We ran this against a table seeded with
both good and bad values before writing it down: it names exactly the
rows that are not documents and does not flag valid ones — including
the easily-missed valid shapes, a bare `42`, `true`, `null` and a
quoted string.

A non-zero count means rows were written before validation existed.
They are still readable; what is not guaranteed is that `->` and `->>`
against them return anything sensible. `SELECT id FROM your_table WHERE
your_json_column IS NOT JSON` lists them.

**b. Anything you concluded from an empty result** on the MySQL wire
(§1.1, §1.2) — particularly joins on text columns, and any query against
a column you added an index to. If a report ever said "0 rows" and
someone acted on it, that number is worth re-running.

**c. Case-insensitive uniqueness.** If you have
`UNIQUE (lower(email))` or similar, it was enforced correctly all along
— you do not have duplicates. It was just expensive, and it stopped
being so.

**d. Nothing to re-check for `ORDER BY`.** Sorting was wrong in the
sense of giving a different order, not a different set: no rows were
lost to it. `ORDER BY … LIMIT` with an index is the exception (§1.2) —
those returned the wrong rows.

## 3. The upgrade itself

**The data directory is compatible and we tested this exact hop.** We
opened a 7.38.6 data directory with the 7.38.17 binary: 490 rows across
nine types, deletes and updates and statement-level WAL, and the md5
over an ordered projection came back `0d009cf6…23abfe` — the value
7.38.6's own binary produced. No conversion step, no dump-and-reload.

The catalog format has not changed anywhere in this span; the last
`FILE_VERSION` bump predates 7.38.6.

**No configuration or client changes.** Zero-customer-change is a
standing rule here: your code, your connection strings and your schema
are untouched.

**Two version numbers you will not find:** 7.38.9 and 7.38.14 were
tagged and never published — their release trains stopped inside the
pre-publish gate and nothing reached the registry. Tags do not get
moved, so that work shipped as 7.38.10 and 7.38.15. There is no gap in
what you receive.

**Going straight to 7.38.17 is what we recommend**, rather than stepping
through. Each release's gate verifies the previous release's data
directory, and the 7.38.6 → 7.38.17 hop is the one we tested directly
for this document.

## 4. Performance, in the span

We started measuring your own workload shapes at 7.38.7, so the
"7.38.6" column below is where you are now. Every figure is against
PostgreSQL 18 over the wire, on your shapes.

| shape | on 7.38.6 | now |
|---|---|---|
| jsonb: containment in a window | 16.4x behind | **level** |
| window: count over a day | 5.7x behind | **level** |
| window: group by kind | 3.7x behind | **level** |
| window: distinct seats | 2.0x behind | **level** |
| btree: project and kind | behind | **level** |
| jsonb: containment (no window) | 2.4x behind | 1.7–1.8x behind |
| ingest: one row | 2.1x behind | 1.6–1.8x behind |
| dashboard: top versions | 2.5x behind | 2.1–2.2x behind |

The bottom three are still behind and we are not calling them done.

What did it: a `GIN` predicate and a `BRIN` range now intersect at the
row locator instead of one of them being ignored (7.38.12); `BRIN`
summaries went from costing without paying to really pruning
(7.38.11 — `count(*)` 4.9 ms to **0.230**, `SELECT id` 9.48 to
**0.335**); `jsonb` accessors stopped re-parsing the document on every
access and a `json` column stopped re-proving itself (7.38.8); and the
scan filter runs the cheap half of a conjunction first (7.38.8).

Separately, a repeated `distinct` + `order` shape that had flickered on
our own gate for three releases was fixed in 7.38.13 (104.9 to 96.8 ms,
about 7.4 %, ranges non-overlapping over six interleaved pairs). By
7.38.15 that cell measured 87.9–94.5 ms against PG18's 114.9–120.8 at
400,000 rows.

Our release gate holds a 64-cell constant-answer sweep against PG18. It
has been **0 losses** for the last several releases, including this one.

## 5. What we fixed about ourselves

We would rather say this than let you find it.

**Our MySQL test corpus had been running in PostgreSQL mode since the
day it was created.** The runner had no notion of a SQL dialect at all.
Twenty-one files asserted that MySQL *syntax* is accepted and nothing
whatsoever about MySQL *semantics*. That is why §1.2's wrong answers —
on the most ordinary query shapes there are — went unreported for as
long as they did. Not because a test looked and passed: because the
question could not be written down.

We found five more of the same shape, and three were in the tools built
to catch it: the first instrument we wrote read a file's declaration
instead of asking the engine; our own written plan called a line in a
wish-list comment a capability; a registry header promised a CI check
that did not exist; a gate step named "opens the previous release's data
directory" had the directory name typed in as a literal; and our
three-engine differential had never once put SPG into MySQL's mode.

Each now has a mechanical check that goes red rather than a note. The
release gate grew from eight categories to nine, the acceptance panel
learned to speak MySQL, and a tier report now ends by naming exactly
which of our test steps did **not** run — because a summary that cannot
show what it excluded is a summary that overstates.

**7.38.18 found three more, and one of them is about this document.**

*The gate's cross-version open only ever made a one-release hop.* The
step that opens a released data directory with the new binary picked the
**newest** previous release. That is the hop least likely to break — it
is almost always the same file format on both sides. The far hop, the
one you are about to make, had no check at all. It now opens the oldest
and the newest fixture we hold, and the verdict line names both.

*Our own lint runs were hiding their findings.* Six times this cycle the
gate reported a lint failure our local runs called clean, and six times
we diagnosed it wrong. The gate treats warnings as errors; our local
command did not, and then filtered the output for lines beginning
`error`, which removed every finding there was. **Two of them were real
errors sitting in committed code.** The reproduction rule is now to run
the gate's own step rather than a reconstruction of it.

*A test written straight after the code it tests can copy the bug.*
Twice we wrote a fixture from what our engine printed rather than from
what the engine we stand in for prints, and one of those fixtures then
argued for the defect for a full release. Expectations come from the
oracle now, in a run recorded before the fix.

## 6. Still open, named rather than left out

The four items this section carried at 7.38.17 are closed. Trailing
spaces under a named collation, the cross-type comparison across tables,
`SHOW WARNINGS`, and the MariaDB acceptance panel all shipped in
7.38.18; §1.3 describes the first of them. What replaces them:

- **Sorting a text column under a locale collation is about 1.3x behind
  PostgreSQL**, measured in-process, and we have not closed it. We know
  where it goes: PG builds an *abbreviated* sort key — a few bytes that
  decide most comparisons without touching the full key — and the ICU
  binding we use does not expose one. Building full keys up front and
  sorting those is 138 ms per 200,000 values against ICU's 175 ms of
  comparisons; an 18 % saving that still loses. We would rather say that
  than describe an 18 % improvement as a fix. Byte-wise collations —
  `C`, and every column that has not asked for a locale — are unaffected
  and are the ones the sweep in §4 measures.
- **`COLLATE` on an arbitrary expression.** `ORDER BY col COLLATE
  "de-DE-x-icu"` works; `ORDER BY (a || b) COLLATE "de-DE-x-icu"` does
  not parse. It needs a collate node in the expression tree rather than
  a property of a column reference, which every expression walker then
  has to carry.
- **Three of your shapes are still behind PostgreSQL 18** — see the
  table in §4. They are not closed and we are not calling them closed.

## 7. If something looks wrong after upgrading

Send us the statement and, if you can, the answer you expected. We keep
a corpus of your query shapes and run it against every release; a shape
we do not have is a shape we cannot protect, and adding one is a
half-hour of our time and none of yours.
