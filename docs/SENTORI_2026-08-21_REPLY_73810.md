## 1. The correction

The harness we gave you in 7.38.7 seeded both databases and measured
immediately. PostgreSQL builds its BRIN summaries in `VACUUM`, so that
measures PG with the index you asked for doing nothing: the same
one-day window query read 7.3-8.9 ms unsummarised and 1.2-5.1 ms after
a `VACUUM ANALYZE`, on the same rows in the same session. On top of
that our side was running natively against a containerised PG.

Both errors point the same way — ours. The real starting point was
**2.0x to 16.4x behind**, not the 1.6x to 8.9x we reported. The
harness now vacuums both legs before anything is timed, and we
re-measured with both databases as containers.

We would rather tell you this than have you find it. A vendor's own
harness being generous to the vendor is the one direction it must
never fail in.

What moved, and why:

- **A temporal constant is carried decoded.** A timestamp comparison
  cost 52 ns a row against an integer comparison's 22; it is now 21.6.
  Three readings of our own code were proposed for that and all three
  were refuted by measurement before the real cause turned up.
- **The scan filter runs the cheap half of its conjunction first.** The
  same query written the other way round cost 4.7 times as much —
  `traits @> …` before a timestamp window, 40.0 ms; after it, 8.5.
  Which one a person writes first is habit. Both spellings now measure
  8.5.
- **jsonb stops re-proving itself.** `->>` parsed the whole document
  into a tree solely to validate it, threw the tree away, then found
  the key by scanning the text; the key comparison ran the parser over
  every key it walked past; and `->>` ran it once more over the result
  to unescape nothing. 758 ns a row to 173.
- **`@>` answers the flat-object case without building a tree for the
  left document.** Containment rides the GIN index, so the cost was the
  recheck on each matched row. One key: 38.2 ms to 17.2.

## 3. A defect your dump found, and a behaviour change

`INSERT INTO t VALUES ('{bad')` into a `jsonb` column was **accepted**.
PG18 answers `invalid input syntax for type json`. We stored the raw
text and every later read of that row raised instead — in 7.38.7 one of
those reads was on the checkpoint thread, where writes keep being
acknowledged while nothing reaches disk.

Validation now happens where PG puts it, at the column boundary, with
PG's message. **This changes behaviour**: a statement that inserted
invalid JSON into a json/jsonb column and succeeded will now raise. If
anything in Sentori relied on that, it was storing a value nothing
could read.

That guarantee is also what the accessors above were paying for on
every row.

## 4. The largest remaining gap, and something you can do today

The worst shape is still the one-day window, 6.7x. Taking it apart:

```
SELECT count(*) FROM events WHERE received_at >= … AND received_at < …

  your schema, BRIN on received_at        5.09 ms
  with a BTREE added on the same column   0.105 ms      <- 48x
  PostgreSQL 18, BRIN summarised          1.2 ms
```

Given an index it can use we answer this **11x faster than PG**. The
index you created is the one that does nothing: our BRIN summaries are
derived and written into a cold-tier segment's sidecar, and **no query
path reads them back** — and for hot data none exist at all. A BRIN
index costs us writes to maintain and saves no reads.

So, plainly: **a btree on `received_at` would make your window queries
0.105 ms today.** It costs more to maintain than a BRIN, which is
presumably why you chose BRIN, so this is a trade to make knowingly
and not a recommendation to paper over our gap. Making BRIN actually
prune is the next campaign and it is written up rather than promised.

Three traps the harness hit while being built, in case you meet them:
psql may itself be a container wrapper, in which case `127.0.0.1` is
not the host (`HOST_ADDR=host.docker.internal`); a host path passed to
`-f` is not a path such a psql can open, and the failure reads as a bad
schema; and it inherits stdin, so it swallows the rest of the shape
list on the first shape — which produced a run that measured one cell
of eight and printed a complete-looking table. The list is read on a
separate descriptor now and the run refuses to report fewer cells than
the profile lists.
