**Your BRIN index now does something.** It did not before, and that is
the headline: the summaries were computed and written into a cold

maintain and saved you no reads.

## 1. What changed

The hot tier keeps one `(min, max)` per 1024 rows, and a range
predicate on that column skips the ranges that cannot match.

Maintenance is **widen-only**, and that is the entire safety argument:
an insert widens its range, an update widens, a delete leaves it
alone. A range left wider than the rows it covers is correct and
merely less selective — which is exactly PostgreSQL's contract for a
lossy index, since the predicate is re-checked on every row the
summary lets through. A summary may over-report; it cannot
under-report. **No matching row can be skipped.**

Two more places where we chose the quiet answer over the clever one. A
range with no summary is never skipped, so a column holding values the
index cannot order behaves exactly as before. And the reader returns
"no opinion" rather than "every slot", so every code path that does
not know about BRIN is untouched.

Measured over the wire, 200,000 rows, a one-day window over 90 days:

```
SELECT count(*) … WHERE received_at >= … AND < …     4.9 ms  ->  0.230
SELECT id       … WHERE received_at >= … AND < …     9.48    ->  0.335
```

PostgreSQL 18 answers the first in 1.0-1.3 ms.

## 3. How we convinced ourselves it is not skipping rows

This is the failure mode that matters: a prune that removes too much
is faster AND wrong, and it looks like a bigger win than the correct
one. So the checks are built around that, not around the speed.

- **The in-process control pair.** Same table, same query, with and
  without the index. On ascending timestamps 9.58 ms to 0.115. On
  **cycling** timestamps — where correlation collapses and no correct
  prune can skip anything — 9.72 to 9.57, level. That second line is
  an assertion in the probe, not a note: a build that speeds it up
  fails.
- **Seventeen corpus cases about the ANSWER**, not the time: interval
  boundaries, equality on the first and last row of a range, a value
  outside every range, a row written out of order after the index
  existed, NULLs, and an UPDATE that moves a value out of its range's
  span. Watched failing — making the summary narrow instead of widen
  turns three of them red, and the failure is rows silently vanishing
  (60 becomes 0).
- **Your own data.** The `kill -9` fixture built from your dump ran in
  this release's battery on two machines, and one of its three index
  probes is the BRIN on `events.received_at`: the index-backed answer
  must agree with a sequential scan of the same predicate, on a
  database reopened after `SIGKILL`. It agrees.
