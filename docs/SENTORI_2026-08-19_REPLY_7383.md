## 2.1 Top-level `IS NULL` / `IS NOT NULL` / `NOT` described no columns — fixed

Your table was the diagnosis. The type walker had no arm for the null
test, and its "I cannot type this" answer abandons the WHOLE
statement's column list rather than the one item — which is exactly why
`(a IS NOT NULL AND b IS NOT NULL)` described and `a IS NOT NULL` did
not: the operator that consumed it never asked what it was.

You named three shapes. Measuring the class found five more with the
same hole, so they are closed together rather than left for report
eight:

| shape | before | now |
|---|---|---|
| `IS NULL` / `IS NOT NULL` / `NOT (…)` | `[]` | described |
| `IS TRUE` / `IS NOT TRUE` | `[]` | described |
| `LIKE` / `NOT LIKE` | `[]` | described |
| `IN (…)` | `[]` | described |
| unary `~` / `+` | `[]` | described |

Types verified against PG18's own view columns: every predicate is
BOOLEAN, the two unary operators keep their operand's type, and an
unaliased one is named `?column?` as PG names it. Your `describe/`
battery reports 0 empty on this build.

Step 41 should pass. `user_key IS NOT NULL AS addressable` needs no edit.

## 2.2 `ADD COLUMN … CHECK (…)` accepted and never registered — fixed

Right on both counts: it predated 2.1's fix, and it is worse than a
loud failure. The predicate was on the parsed column all along; the
ADD COLUMN path never read it, while the `ADD CONSTRAINT` spelling your
three migrations use was enforced the whole time.

Now, matching PG and differential-anchored: the constraint lands as
`<table>_<column>_check`, `pg_constraint` shows it, a violating INSERT
is refused with PG's wording — and it is **validated against the rows
already there**. Adding `e text CHECK (e IS NOT NULL)` to a populated
table errors ("is violated by some row") exactly as PG does, and the
refused column does not stay behind; the same column with a DEFAULT
that satisfies the check succeeds.

## 3. Four more, found by asking your statements instead of waiting

Your §1 shows the pattern plainly: each release you advance a few steps
and hit one more Describe defect — a data-modifying CTE at 16, a
subquery in the select list at 30, a null test at 41. Every one of them
was answerable without any data, because Describe answers from the
schema alone. So we stopped waiting.

We extracted all 211 distinct SQL literals from your sources, replayed
your 17 migrations onto both SPG and PostgreSQL 18, Described every
statement on both, and diffed. Thirteen answers differed. Four causes,
each measured against PG18 before it was implemented, and each on a
page your suite has not reached:

| | what we said | what PG says | where it would have hit you |
|---|---|---|---|
| unaliased function call | `?column?` | `count`, `max`, … | 8 statements, incl. `health.rs`, `push_devices.rs` — and our own execute path already said `count`, so Describe and the RowDescription disagreed with each other |
| `->>` and `#>>` | JSONB | TEXT | `projects.rs:344` — a decode into `String` meets a jsonb OID |
| `array_agg(uuid)` | TEXT[] | UUID[] | `admin/users.rs:42` — a decode into `Vec<Uuid>` fails |
| `percentile_cont` … `WITHIN GROUP`, and a set-returning function in FROM | **nothing at all** | full column list | `instruments.rs:67` and `projects.rs:311` — the same whole-statement emptying as step 41 |

On 7.38.3, **209 of your 211 statements describe byte-identically to
PostgreSQL 18**, and none of them errors on SPG that PG accepts. The
two that remain are statements PostgreSQL itself rejects: one reads
`_sqlx_migrations` (absent from a schema built by replaying the files),
and one is `pipeline.rs:547`, where `$4` appears both in a VALUES list
and inside `CASE WHEN $4 > 0`, and PG refuses the inconsistent
deduction while we accept it. That last one is us being too permissive;
tell us if you would rather we matched PG's refusal.

The harness that found these ships with us as `xtests/appsql` and will
be pointed at your sources on every release from now on, so this class
reaches you as a fix rather than as a wall.

## 5. What 7.38.3 does NOT change

The collation gap is exactly where it was. Those eight probes are the
shapes our `COLLATION_RFC.md` §4 enumerates and the cause is that our
database default collation is C; §5's recommendation — thread a
collation name from the parser into the catalog, wire an ICU collator
behind it, build the index-rebuild path a collation change demands — is
its own piece of work and is not in this release. `COLLATE "C"` is
pinned in the corpus that gates every release, so the escape hatch
3.3.1 leans on cannot regress silently.
