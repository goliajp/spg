## 1. What it actually was

Three releases each spent a round proving that cell was "not a
regression" without once taking it apart. Taken apart against
PostgreSQL 18's real plan, the obvious suspect turned out to be the
wrong one — again, and it is worth saying why, because it is the
second time this month.

PostgreSQL answers that query by sorting and then discarding rows equal
to the one before them. That costs it almost nothing. We build a hash
set first — four hundred thousand insertions on a column that has no
duplicates to find. That reads like the whole story, and nobody had
looked past it.

It is 2.4 % of the query. Deleting it outright would buy us two and a
half percent.

What was actually wrong sat twelve lines from code that already had it
right. Under `DISTINCT` we build the sort keys *after* the duplicate
check, so only surviving rows pay for them — a good decision. But that
one branch resolved each key's column **by name, once per surviving
row**, while the branch immediately above it has used the resolved
position since the day that optimisation was written. Nothing in the
code or the tests defends the difference; it looks like an omission and
we are treating it as one.

Measured by running the patched and unpatched binaries alternately,
flipping which went first halfway through, with both binaries kept side
by side and checksummed so that a build that did not actually rebuild
could not pose as a result:

| | six runs (ms) |
|---|---|
| before | 103.7 104.7 104.7 104.9 105.1 106.0 |
| after | 96.5 96.6 96.8 96.9 96.9 97.4 |

The ranges do not overlap and every one of the six pairs points the
same way. About 7.4 %.

These are in-process timings from a probe, not wire timings — do not
compare them against a number from the sweep, which measures the same
query with a client and a network round trip in front of it. The probe
is the sharper instrument for a change this size; the sweep is the one
that decides whether the cell passes.

## 2. Two wrong answers, found by measuring

Neither of these is reachable from a benchmark, and neither would have
been found by running one. Both turned up because a performance rewrite
routed one spelling of a query into another and the answer changed.

A column declared `COLLATE utf8mb4_bin` compares byte by byte, so
`'a'` and `'A'` are two different values.

- **`DISTINCT` merged them** and returned one row where MySQL and
  MariaDB return two.
- **`ORDER BY` sorted them by the wrong collation**, and so did
  `MIN()`. We sorted `a, A, bar, Bar`; the reference engines sort
  `A, Bar, a, bar`.

Our first diagnosis of the second one was wrong, and a two-minute
experiment said so before any code moved: an explicit `COLLATE "C"` was
being ignored too, and `C` is both recognised and byte order. There
were two independent causes stacked on top of each other, and removing
either one alone still leaves the answer wrong.

If you have no MySQL-dialect tables with an explicit binary collation,
neither defect could reach you. We are reporting them anyway because
the shape of the failure — a value silently merged with another, or
ordered by a rule the column did not ask for — is the kind we would
want told to us.

## 3. How we convinced ourselves

- **Every expectation from a reference run**, never computed by hand.
  That rule has earned itself twice this month: an earlier draft of one
  of these fixtures hand-computed the order and the runner disagreed.
- **Watched failing three ways**, and each control needs a *different*
  half of the fix — reverting one half turns six records red, disabling
  the other turns five red, and doing the opposite thing entirely turns
  the negative control red.
- **The negative control is tie-free on purpose.** Pinning `'a'`
  against `'A'` would pin a tie order no engine specifies. `'B'`
  against `'a'` is decided by the collation and by nothing else, and
  the two rules disagree about it.
- **The limited form checked separately.** `ORDER BY … LIMIT` reaches
  the answer by a different route — it discards rows before the
  collation-aware sort runs — so we checked at three rows and again at
  four thousand, across both dialects and both column kinds.

## 4. Still open on our side

- **The three jsonb rows.** Unchanged from last time and unchanged on
  purpose: mostly expression dispatch, not the jsonb representation,
  three attacks refuted. The next round re-decomposes rather than
  polishing the same face a fourth time.
- **The de-duplication itself.** We closed the cell without closing
  this: PostgreSQL still de-duplicates for free as a consequence of
  sorting, and we still build a hash set. The reason to fix it is not
  the 2.4 % — it is that three of our sorting strategies currently
  refuse this query *because* of that hash set, and removing it removes
  the reason they refuse. That is the next round's work, and it is
  sized against a control in the same run rather than against this
  cell's own history.
- **The collation gap** — unchanged: we sort by code point, not by a
  locale table, in 8 of 18 probes by design.
