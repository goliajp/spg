# v7.38 P0 中断 protocol — mailrs / sentori dogfood 反馈处理

> 状态:**设计完成 2026-06-22**,作为 v7.38 13.5 周工作期间的 contingency 规则。
>
> 触发:`.claude/notes/v7.38-plan.md` §五 风险 1 — "mailrs P0 中途回执 — 7.37.x ship 后若新 P0 出现,改 7.38 节奏或挂 patch"。
> Audit SEV-3 指出此 protocol 未具体设计,本文件 close。
>
> 配套 case study:**v7.37.5 ship 已经实证此 protocol 一次**(2026-06-21)— 见 §6。

## 1. 中断的 cost

v7.38 是 13.5 周的 test constitution 建设,中段被 P0 打断会:
- 元机制 A/B/C/D 互相 entangle,build sequence 中断重启需要重读 design notes
- 多个 P0 cycle 累积 → v7.38 ship 推延 → 后续 v7.39 / v7.40 全推
- 但**漏放 P0** → 客户 prod 事故,SPG drop-in identity 破产

**判断核心**:**严守"infra 而非承包商"心智**([[feedback-infra-not-contractor]])
— P0 中断不是为了 "修客户那条 SQL",是为了**保 SPG 体系不破洞**。一条具体 SQL = 触发器,
真问题是 SPG 的 X 通用形态。

## 2. 中断判断标准 — 什么算 P0 强制中断 v7.38

### 2.1 P0 — **必须立即中断**

| 信号 | 标准 | 例子 |
|---|---|---|
| **A. data loss** | 任何 committed 数据丢失 / 不可重建 | round-24 WAL Display 丢 ON CONFLICT brick catalog;round-21 prod incident u16 sweep |
| **B. data corruption** | 数据读出来跟写进去字节不一致 / 类型错乱 | round-26 服务端 prepared 写不进 WAL 但回 OK(写丢失 silent) |
| **C. lock hang ≥ 30s** | 客户 prod 任意请求 hang ≥ 30s 且 SPG 无超时 | round-30 livelock 10G inbox query 永不返回 |
| **D. > 2× perf regression on dogfood-replay 已锁定 fixture** | mailrs / sentori 实测某 endpoint 比 v7.37.5 baseline 慢 2× 以上 | v7.37.3 spg-sqlx budget cancel 引起的 60-175ms double-execute |
| **E. crash / panic in prod loop** | SPG panic / segfault / OOM in 客户日常 query 流 | round-30 OOM in correlated subq pre-materialise |
| **F. dropin acceptance 失败** | dropin-acceptance.sh 在 v7.37.5 baseline 上失败 | dump-compat / data-compat byte 不等;v7.37.5 baseline 59/59 退化 |

### 2.2 P1 — **不打断 v7.38,但同期分支处理**

| 信号 | 标准 | 例子 |
|---|---|---|
| 客户工作 endpoint 慢 10-50% 不影响业务 | 输 PG18 但用户继续跑 | v7.37 train 期间一些 dogfood-replay 红线还没闭 |
| 新 SQL feature 不支持但有 workaround | parser error + 客户重写 SQL 可绕 | 某些非常 niche PG 用法 |
| 文档 / CHANGELOG 错 | 影响理解但不影响行为 | STABILITY.md 漏记新 surface |

**P1 处置**:加 backlog,作为 v7.38 ship 后下一 train(v7.39+)的优先级输入。
**不打断 v7.38 当前 phase**。

### 2.3 P2 — **进 backlog,不优先**

性能改进 idea / 非阻塞 feature request / 优化提议。

## 3. 中断后 patch train 形态

### 3.1 分支策略 — 从 master 起 hotfix branch

**关键决策**:从 **`master` 起 `v7.38.X-hotfix-<topic>` branch**(不从 `develop` 当前 v7.38 工作分支起):
- master = 上一稳定 ship(v7.37.5 起 v7.38 时 = `v7.37.5`)
- 隔离 v7.38 未完工的 in-flight 改动
- hotfix ship 后 cherry-pick / merge 回 develop,让 develop 也受益

```
v7.37.5 (master tag)
   │
   ├── develop tip (v7.38 work, in-flight elements A/B/C/D)
   │      │
   │      └── [P0 触发 → 中断]
   │
   └── v7.38.X-hotfix-<topic> branch (from master)
          │
          ├── attack(s) → ship as v7.37.6 (next patch on v7.37 line)
          │
          └── merge back / cherry-pick → develop
              v7.38 work resumes from new master tip
```

### 3.2 patch 版本号 — 不出 v7.38.0,先 v7.37.6

理由:
- v7.38.0 是 minor bump,意味着 test constitution ship — 那是大事件,不该顺手 ship hotfix 借这个版本号
- v7.37.6 是 patch — 客户期望 patch 是 bug fix,不含新 feature

例:v7.37.5 ship 后 P0 出 → hotfix 编 `v7.37.6`,master 走到 `v7.37.6` tag,然后回 develop 继续 v7.38 work。

### 3.3 hotfix branch 命名

`hotfix/v7.X.Y-<topic>` 一致格式:
- `hotfix/v7.37.6-mailrs-100k-cascade` — clear, specific
- 不允许:`hotfix/quickfix` / `hotfix/issue123`

### 3.4 hotfix ship 流程(简化 release.sh)

```
git checkout master
git pull
git checkout -b hotfix/v7.X.Y-<topic>

# attack on hotfix branch
# ... commits ...

# pre-ship gates (lighter than minor — no full 13-week v7.38 acceptance)
scripts/gate.sh all              # fast tier 5min
scripts/gate.sh all --full       # full tier — at minimum the affected sub-system
scripts/dropin-acceptance.sh     # dropin 59/59 unchanged
cargo run -p spg-dogfood-replay -- all  # mailrs / sentori dogfood

# update CHANGELOG + bump version
# ... fmt ...

# tag + push
scripts/release.sh patch   # if release.sh supports patch lane

# merge back
git checkout develop
git merge master            # OR cherry-pick specific commits
# v7.38 work resumes
```

## 4. v7.38 work 怎么 resume

### 4.1 决策树

```
hotfix touched files / 范围:
├── ONLY hotfix 子系统(不动元机制 A/B/C/D 代码)
│   └── git checkout develop && git merge master
│       (or rebase develop on master)
│       v7.38 work resumes from same in-flight state
│
├── 改动了元机制 A/B/C/D 已 land 的代码
│   └── git rebase develop onto master + 手动 resolve overlaps
│       验证 in-flight A/B/C/D 仍 acceptance pass
│
├── 改动了 hot path 影响 perf baseline
│   └── 跟 master 后立刻跑 perf gate full tier 验证 13-shape sweep 仍 13/13 不输
│   └── 如有退化,触发 perf 工作流(per docs/PERF_METHODOLOGY_VS_FOSS.md)
│
└── 改动了 STABILITY 文档 / 字段
    └── 更新 v7.38-stability-audit-2026-06-22.md "v7.37 train 期间 changes 影响" 表
```

### 4.2 merge vs cherry-pick

- **merge master → develop** — 默认。保 full history,develop 自动获得 hotfix
- **cherry-pick** — 仅在 hotfix 有 develop-only 内容(eg. test-only code)需要分开时

不允许:**rebase develop public branch** — 破坏其他 worker 状态。

### 4.3 in-flight 工作的 sanity check

中断 / 恢复后:
- [ ] `gate.sh all` fast tier 仍 ≤ 5min 不破预算
- [ ] 已 land 的元机制 acceptance test 仍 pass(eg. injection_points unit tests)
- [ ] develop tip 跟 master 完全继承 hotfix 改动(no double-implementation)
- [ ] CHANGELOG 反映:v7.37.6 ship 在 v7.38 work 之前

## 5. P0 dispatch protocol(SOP)

### 5.1 trigger 到 ship 的 SOP

```
T+0    收到 mailrs / sentori P0 反馈
       └── 第一步:【pp 标 P0 / P1 / P2】per §2 判断标准

T+1h   IF P0 confirmed:
       ├── 当前 v7.38 work 提交所有 in-progress changes 到 develop(WIP commit OK)
       ├── git checkout master
       ├── git checkout -b hotfix/v7.X.Y-<topic>
       └── 启 P0 attack 模式

T+1h-T+24h  Attack phase
       ├── 复现:从客户 SQL 抽形态,构成 minimal repro
       ├── 抽体系:形态触发的是 SPG 哪条通用路径(per [[feedback-infra-not-contractor]])
       ├── decomposition agent(read-only)若 perf P0 → 18-stage + atomic-op breakdown
       ├── attack agent(worktree)实施 fix
       └── 每 commit 后 dropin-acceptance.sh + dogfood-replay 验证

T+24h-T+72h  Ship
       ├── 升 v7.37.X patch 版
       ├── scripts/release.sh
       ├── mailrs / sentori ack 写 + 双向送达
       └── memory 更新:project-perf-campaign 标 v7.37.X SHIPPED

T+72h  resume v7.38
       ├── git checkout develop
       ├── git merge master
       ├── 验 sanity check §4.3
       └── 从中断 phase 继续 work
```

### 5.2 P0 攻坚 budget

- **24h SLA T+0 → 候选 fix 在 hotfix branch 上**
- **72h SLA T+0 → v7.X.Y patched + shipped + ack sent**
- 超 72h → 升级:不靠多发 commit 解决,**重新 decomposition + 找根因**(per [[feedback-perf-hard-means-do-micro-decompose.md]])

### 5.3 attack 期间的 constraints

per `feedback-perf-is-the-reverse-scale` + `feedback-only-look-at-losses`:
- 不许 ack 中"自夸赢的端点",P0 中断期间**只看输的 / 坏的**
- 不许 "客户可以接受"、"暂时 workaround"等话术(per `code/no-blind-bugfix-pattern`)
- 修复必须**治本** — 客户的具体 SQL 只是触发器,改 SPG 体系的通用路径
- 修复必须配 perf gate / regression test 钉住,避免再次回归

## 6. Case study — v7.37.5 ship 已实证此 protocol

**实际事件(2026-06-21)**:

v7.37 train 期间触发的 P0 / 准 P0 处置回放:

### 6.1 v7.37.0 → v7.37.3 train 内部 perf 红线
- mailrs ack 后实测 3 端点输 PG → 准 P0(per `feedback-perf-is-the-reverse-scale` 等同 P0 处置)
- 7.37.0 / 7.37.1 / 7.37.2 / 7.37.3 顺序 ship,**每一次都是用本 protocol 的精神**(虽未明文)
- 7.37.3 找到根因(spg-sqlx 默认 inline budget 25ms double-execute),改 25→1000ms 0 客户字符差异
- 当时 v7.38 work 还未开始(v7.37 主线),所以没有 "resume v7.38" 这一步,但每次 hotfix → mailrs ack 是同款流程
- **教训**:7.37.2 ack 把锅甩客户违例 → 触发 `feedback-only-look-at-losses` 等三铁律,所有 ack 模板必须 absorb

### 6.2 v7.37.4 红线 closure(SCALARSQ / DISTA / INSUBQ)
- 用户原话 "noise 的两项与 2.75x 的我不接受" 触发 → 准 P0
- decomposition agent(read-only)产 18-stage + atomic-op breakdown
- attack agent atomically 实施 3-4 个 fast path
- **直接验证 protocol 的 §5.3 attack constraints** — 不许 "language ceiling" / "structural gap"
- ship 后写 `docs/PERF_METHODOLOGY_VS_FOSS.md`,把整个 workflow 文档化

### 6.3 v7.37.5 ship 后(本协议生效起点)
- v7.37.5 ship 完(2026-06-21,master @ `48d422b` + tag `v7.37.5`)
- mailrs ack 已 land
- **没有触发新 P0** — develop 在 `44cb12b` 进 v7.38 P0 阶段
- **本 protocol 设计就是这一刻起作为 v7.38 期间 contingency 生效**

### 6.4 protocol 已验证的属性

| 属性 | v7.37 train 实证 |
|---|---|
| 严守 infra-not-contractor 心智 | 7.37.3 把 spg-sqlx budget 当 spec channel 修,不改客户代码 |
| 治本而非压症状 | 7.37.4 SCALARSQ -85% 是 decomposition 找到 BTreeMap descent,不是 try-catch |
| 24h-72h SLA 现实可行 | 7.37.0 / 7.37.2 / 7.37.3 都 < 72h ship |
| ack 模板 — 不甩客户 | 7.37.2 教训 + 三铁律 absorb 进 memory |
| 配 perf gate baseline 钉住 | v7.37.4 13-shape sweep 13/13 不输 = TESTING_V2_SKELETON.md §253 frozen baseline |

## 7. v7.38 期间预期的 P0 类型

per `.claude/notes/v7.38-plan.md` §九 v7.37 残留 known issues:

| 候选 P0 source | likelihood | 处置 |
|---|---|---|

## 9. 不在本 protocol 范围

明确不涵盖:
- **非 dogfood 通道的反馈**(eg. external GitHub issues / 邮件投诉)— 走正常 backlog
- **v7.38 内部工程问题**(eg. P0 元机制 build 卡)— 不算客户 P0,plan 内部调整即可
- **mailrs / sentori 自己的代码 bug**(SPG 行为正确客户 SQL 错)— 给客户反馈,不出 SPG patch
